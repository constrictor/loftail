# loftail — Architecture & Technical Decisions

**Status:** Draft, 2026-07-20.
**Scope:** Internal decisions and their rationale. Nothing here is user-visible; product behavior lives in `SPEC.md`.

## 1. Stack

| Decision   | Choice                     | Rationale                                                                   |
| ---------- | -------------------------- | --------------------------------------------------------------------------- |
| Language   | C++20                      | Matches the log4cplus ecosystem; needed for the performance profile in §7.  |
| Toolkit    | Qt 6 Widgets               | See §2.                                                                     |
| Minimum Qt | 6.4 (dev machine has 6.10) | The version in Ubuntu 24.04's repos (6.4.2); nothing needed requires newer. |
| Build      | CMake ≥ 3.21 + Ninja       | `qt_add_executable`/`qt_add_test`; Ninja for build speed.                   |
| Tests      | Qt Test                    | In-tree, no extra dependency, integrates with CTest.                        |

**Reference build environment: Ubuntu 24.04 LTS.** The project must build with the toolchain 24.04 ships — GCC 13, CMake 3.28, Ninja, and Qt 6.4.2 from the system repos — using no separately-installed Qt. This is why the minimum Qt is 6.4 rather than the 6.5 LTS: pinning to 6.5 would force a non-apt Qt on the reference distro for no functional gain. Nothing in the design uses a 6.5+ API; if that ever changes, this constraint must be revisited, not silently broken.

### 1.1 Release identity and build identity are two strings

`--version` has to answer two different questions, and one string cannot: *which release is this* and *which build is this*. The release is `project(VERSION)` at the top of `CMakeLists.txt`; the build is the CI run number and abbreviated commit, composed at configure time into `LOFTAIL_BUILD_ID` and reaching the binary as a second compile definition beside `LOFTAIL_VERSION`. `applicationVersionString()` joins them with `+` — SemVer build metadata, defined to be ignored in comparison, so the string still names the release to anything that parses it. Four things are load-bearing:

- **The build id reaches `--version` and nothing else.** Package *filenames* — the `.deb`, the AppImage, the `.app` bundle — keep naming the release alone. That is not tidiness: `packaging/linux/deb.cmake` builds `CPACK_PACKAGE_VERSION` as `${PROJECT_VERSION}~${LOFTAIL_DEB_DISTRO}`, and the deb job asserts on the shape of the resulting name, so a build id smuggled into `PROJECT_VERSION` would break that check and put a run number in the filename of every published package.
- **Empty is the ordinary value, not a fallback.** A build from source carries no build id and prints a bare `loftail 0.1.0`, which is precisely how it says it is not a CI artifact. Reading "empty" as "unknown" and printing something for it would erase the distinction the stamp exists to draw.
- **Nothing is read from git.** A configure-time `git describe` goes stale as soon as the tree moves under an already-configured build directory, and it would make git a build dependency for a source tarball that has no `.git` in it.
- **The stamp is what makes releasing a *promotion* rather than a rebuild.** `release.yml` publishes the artifacts of an already-green run rather than building the tag, which is only safe because the downloaded binary can be made to say which run it came from — `--version` is read back and both halves are checked, the release against the tag and the build id against the run being promoted. Without it, "which run is this artifact from" is unanswerable and promotion is guesswork. See `packaging/README.md`, "Releasing".
- **The values default from the environment**, so one job-level `env:` block in `packaging.yml` stamps every configure in the workflow — including the two that happen inside `build-appimage.sh` and `build-appbundle.sh`, whose cmake command lines no caller can reach. A `-D` still overrides. Being cache variables they are fixed at first configure; CI configures a fresh build directory per run and caches none, so they cannot go stale there.

**loftail does not link log4cplus.** It parses log files as text. There is no compile-time or runtime dependency on the producing library, which keeps the build trivial on all three platforms. (If loftail ever wants its own diagnostic logging, use `QLoggingCategory`, not log4cplus.)

## 2. Qt Widgets over QML

Both can render a virtualized table over a lazy model; `QTableView` and Qt Quick `TableView` are comparable there. The decision rests on three things Widgets provides that QML would require building:

1. **Cross-row text selection and copy.** `QTableView` gives rubber-band and shift-click range selection natively. QML has no cross-delegate text selection — it would mean hand-rolling hit-testing, selection anchors, and clipboard serialization. For a log viewer, selecting a span of records and copying them is a primary interaction, not a nicety.
2. **Dockable panes.** `SPEC.md` §8 describes `QDockWidget` almost exactly: show/hide, move, float, tab — and a `QMainWindow` central widget keeps them out of the document area for free (§12.2). QML has no docking framework; `SplitView` gives fixed panes only.
3. **Layout persistence.** `QMainWindow::saveState()`/`restoreState()` covers most of `SPEC.md` §10 in a few lines. QML would need bespoke serialization of every pane property.

Secondary: Widgets renders cells via `QStyledItemDelegate::paint()` without instantiating a QObject per visible cell, which is lighter for a dense fast-scrolling table; and Widgets picks up native platform styling on all three targets.

QML would win for animation-heavy or touch/embedded targets. Neither applies. **Do not revisit this without a concrete reason** — the cost is concentrated in items 1 and 2, which are easy to underestimate.

**Caveat added 2026-07-20:** the full-height multi-line requirement means the record table is a custom `QAbstractScrollArea` rather than `QTableView` (§7.1), so argument 1 above is weakened — some selection behavior is hand-rolled either way. The decision still holds: arguments 2 and 3 are untouched, `QItemSelectionModel` and the delegate/clipboard machinery remain reusable, and a custom scroll area in Widgets is substantially less work than the QML equivalent.

## 3. Pattern compilation

The `ConversionPattern` is treated as source code, compiled at runtime to a regex plus a field map:

```
"%d{%Y-%m-%d %H:%M:%S} [%t] %-5p %c - %m%n"
              ↓ PatternCompiler
recordRe:  ^(?<ts>…) \[(?<thread>[^\]]*)\] (?<prio>\S+)\s+(?<logger>\S+) - (?<msg>.*)$
fields:    [ts, thread, prio, logger, msg] + role indices
```

```cpp
struct LogFormat {
    QRegularExpression recordRe;        // full record
    QRegularExpression recordStartRe;   // prefix up to the message field — see §4
    QVector<Field>     fields;          // ordered; drives column headers
    int prioGroup   = -1;               // -1 when the pattern omits the field
    int loggerGroup = -1;
    int threadGroup = -1;
    int dateGroup   = -1;
    int msgGroup    = -1;
    DateFormat impliedDateFormat;       // how to parse the %d text
    Qt::TimeSpec impliedZone;           // local or UTC, per the date specifier — §5.1
};

class PatternCompiler {
public:
    static Expected<LogFormat, CompileError> compile(QStringView pattern);
};
```

Must handle the modifiers that appear in real configs: left/right padding (`%-5p`), truncation (`%.30c`), combined width and precision (`%20.30m`), literal `%%`, and `%d{...}` with a strftime-style inner format translated to its own sub-regex.

**The specifier set is closed and matches log4cplus's `PatternLayout`** (`include/log4cplus/layout.h`): an unrecognized specifier is a `CompileError`, not a silently ignored column, so a pattern from a different logging library fails loudly. Two consequences of covering the whole set:

- **Not every specifier earns a `Record` field.** Only date, priority, logger, thread, and message are stored at index time; `%F %L %M %l %T %i %h %H %r %x %X %E %b` compile to ordinary capture groups and are re-extracted from the record's first line inside `data()` when their column is painted. This keeps `Record` at 32 bytes (invariant #1) — a pattern with ten specifiers costs no more index memory than one with five.
- **The context specifiers need a different sub-regex.** `%x` (NDC), `%X` (MDC), and `%E` (environment variable) carry arbitrary application text: it may contain spaces, and it is *empty* whenever no context was pushed, which collapses `[%x]` to `[]` in the output. `\S+` — correct for every other field — matches neither case, so these three compile to a lazy `.*?` bounded by the literal that follows them. The trade is ambiguity when two free-text fields sit adjacent with no separator; the lazy quantifier makes that degrade to the shortest match instead of swallowing the following fields.

Specifier arguments (`%c{2}`, `%X{key}`, `%E{VAR}`) are consumed even where they change nothing about the regex — `%c{2}` still matches one whitespace-free token — because leaving the braces in the literal stream would compile `{2}` into text the log line does not contain. `%X{key}` and `%E{VAR}` name their column after the key.

**`PatternCompiler` is pure:** string in, `LogFormat` or a structured error out. No I/O, no Qt GUI types. It is the most testable unit in the project and should be built and covered first.

**Key indirection:** no component downstream of the parser ever sees the pattern string. Views, filters, and highlighters consume only `LogFormat::fields` and the role indices. This is what makes autodetection (§9) a drop-in.

## 4. Records vs. lines

log4cplus messages may contain embedded newlines (its own documented examples do), so a record can span several physical lines.

**Indexing rule:** a line matching `recordStartRe` opens a record; subsequent non-matching lines are continuations appended to it.

`recordStartRe` is derived by compiling the pattern only up to the message field — the prefix is what reliably identifies a record boundary, since the message itself is unconstrained.

Consequences that must hold everywhere: row count ≠ line count; a record's byte range covers its continuations; filtering operates on records, so a filtered-out record hides its continuation lines too. Code assuming one line per row is incorrect.

Lines that match nothing and precede any record start (or appear when the pattern is wrong) are retained as `Unparsed` records so the view can display them as plain text — `SPEC.md` §4 requires that a bad pattern never yields an empty window.

## 5. Index

```cpp
struct Record {
    qint64  offset;    // byte offset into the source
    qint64  timestamp; // epoch ms; INT64_MIN when the pattern has no date field
    quint32 length;    // spans continuation lines
    quint32 loggerId;  // interned
    quint32 threadId;  // interned
    quint16 lineCount; // physical lines; drives row height (§7.1). Clamped to 65535.
    quint8  priority;  // Priority enum, declared in severity order (§7.2); Unknown < Trace, for unparsed
};                     // 32 bytes, exactly — no padding waste
```

Everything here is collected during the indexing scan, which is already reading every byte.

- `lineCount` costs nothing to count.
- `timestamp` is parsed eagerly because time-range filtering and jump-to-time need it, and adding it later would mean reindexing every file. The compiled `%d` sub-format tells the parser exactly how to read it. **It is always stored as UTC epoch milliseconds** — see §5.1.
- `threadId` is interned exactly like `loggerId`, giving thread filtering the same integer-compare fast path and the same free discovery of the value set.

**Budget:** ~32 MB of index per million records, up from 24. Worth the two filter axes it buys, but note it before anyone opens a 10 GB log.

### 5.1 Time zones

`SPEC.md` §4 makes both the source time zone and the timestamp display user-configurable. One rule keeps that from leaking everywhere:

> **`Record::timestamp` is always UTC epoch milliseconds.** Zone conversion happens exactly twice — once on the way in, once on the way out.

- **In:** the indexer applies the *source* zone (inferred from the pattern's date specifier, or explicitly set) to convert parsed wall-clock text to UTC.
- **Out:** the view applies the *display* zone when formatting a timestamp for a cell, and the filter UI applies it when interpreting typed range bounds. **The display zone is derived, not stored:** `Document` holds a `TimeDisplay` mode (`SPEC.md` §4) and `displayZone()` returns local, UTC, or the source zone accordingly. It is *cached* rather than computed per call, because `LogModel::cellText` reads it once per painted Date cell and `QTimeZone::systemTimeZone()` is not free.

The two *seconds* modes convert nothing at all: `Record::timestamp` is already UTC epoch ms, so seconds are a subtraction and a divide. The out-conversion is therefore **conditional**, not universal — which does not weaken the invariant, because it only ever removes a conversion, never adds one somewhere else.

**The filter and highlighter time bounds are asked for in whatever terms the column is using** (`SPEC.md` §6), which makes the "out" side symmetrical: `AxisEditor` holds two editors per bound — a `QDateTimeEdit` for the three wall-clock modes and a `QDoubleSpinBox` of seconds for the other two — and shows the pair the mode calls for. Four things keep that from becoming a second time model:

- **A bound is an INSTANT**; the editors are two ways of asking for one. `boundInstant()`/`setBoundInstant()` are the only readers and writers, and everything else in the class works in UTC ms.
- **`MatchCriteria` keeps storing display-zone wall clock**, unchanged, because a count of seconds is not portable: it is relative to a baseline belonging to this file, this run partition and this display mode, none of which a preset carries or a session can promise to restore. So the date editors remain the bound `criteria()` reads, and every write to the seconds pair — programmatic or typed — mirrors into them.
- **`m_renderMode`/`m_renderBase` sit beside `m_renderZone`** and mean the same thing: what the digits currently on screen are written in. `boundInstant()` reads *those*, never the document's current mode, because `refreshTimeBounds()` runs exactly when the two disagree — reading the new mode there would interpret seconds as a date at the one moment a bound must survive intact.
- **`RunSeconds` bounds count from the SELECTED run.** The column is per-record — each record counts from its own run — and one bound cannot be; the selected run is what already restricts the view (`SPEC.md` §3a), so it is the baseline that agrees with what is on screen. `MainWindow::onRunSelected` therefore calls `refreshTimeBounds()` on both panes, exactly as a display-mode change does: the digits are rewritten, the instant is not moved. `followLastRunIfMoved()` calls it for the same reason and is easier to forget, since nobody clicked anything — the selected run moves there on its own, when a followed log restarts (§7.3).

Comparison, sorting, filtering, and any future multi-file merge therefore operate on a single monotonic integer scale with no zone awareness whatsoever. Storing local wall-clock time instead would make every comparison zone-dependent and would break outright across a DST transition, where the same local timestamp occurs twice.

**Changing the source zone requires reparsing timestamps** — but only timestamps, not a full reindex: record boundaries and byte offsets are unaffected, so it is a pass over the existing index. Changing the display mode is free, a repaint: `MainWindow::applySettings` can never route a `TimeDisplay` change to a rescan or a reparse.

**`RunSeconds` makes a timestamp cell depend on the run partition** — the first time a cell's rendering has depended on anything but its own `Record` plus a zone. The baseline is memoised per run behind `Document::runBaseTimestamp()` (O(log runs) plus a one-entry hint, since `LogView` paints contiguous row ranges), with a resume cursor so a run whose leading records are unparsed is walked once in total rather than once per cell. The memo is invalidated by `detectRuns()`, `reparseTimestamps()`, `rescan()` and `prepare()` — but deliberately **not** by `updateRunsAfterAppend()`, because appending only grows the run list and cannot un-resolve a baseline already found. Everything that repartitions the runs already ends in a model reset or a full repaint, so no `dataChanged` plumbing is needed.

A run's baseline falls *forward* to the first timestamped record inside it rather than using the stored `Run::startTimestamp`, which is `kNoTimestamp` whenever the marker record's own date failed to parse. Note the marker must still *start* a record to be visible to run detection at all: a wholly non-matching line is a continuation of the record above it (invariant #2), so the reachable case is a structurally well-formed line whose date is not a real one.

`PatternCompiler` reports which zone the date specifier implies, since log4cplus distinguishes local-time and UTC date specifiers: **`%d` is UTC and `%D` is local time**, per `log4cplus/layout.h`. The mapping reads backwards — the lowercase, more common specifier is the *UTC* one — and loftail had it inverted until 2026-07-28, silently shifting every `%d`/`%D` timestamp by the local UTC offset. `tst_patterncompiler`'s `impliedZone` rows pin it. That is what the *Infer from pattern* default consumes. Treat the inference as a hint that the user can override, not ground truth — the pattern reveals the specifier, not how the producing application was actually configured.

Parse eagerly **only** what filtering needs — priority and logger. Everything else (timestamp, thread, message text) is parsed lazily in `QAbstractTableModel::data()` from the mapped bytes. Storing parsed strings per record is the single most likely way to make this application unusable on large files.

**Interning:** logger names map to `quint32` via a `QHash<QString, quint32>` built during indexing. Filter predicates then compare integers rather than strings, which matters at millions of records. The intern table is also the authoritative subsystem list for the filter pane (`SPEC.md` §6) — discovery is a side effect of indexing, not a separate pass.

**Budget:** ~24 MB of index per million records. Note this before anyone opens a 10 GB log; if it becomes a problem the fallback is a chunked/paged index, but do not build that speculatively.

## 6. File access

```cpp
class LogSource {                       // the model cannot tell which impl it has
    virtual QByteArrayView bytes(qint64 offset, quint32 length) = 0;
    virtual qint64 size() const = 0;
    virtual bool   isRandomAccess() const = 0;  // false for gz/remote (§6.2)
};
```

**Every local file is opened append-aware.** `SPEC.md` §3 removes the post-mortem/live distinction: loftail cannot know whether a file is finished, so it treats all of them as potentially-growing. **No `LogSource` may assume the file is immutable**, and none may hold the file in a way that blocks the writing process from appending, rotating, or truncating it — observing a log must not disturb the process producing it.

Two **local** implementations, selected by **platform**, not by mode (a third, for remote logs, is §6.3):

- **`MappedLogSource`** (POSIX) — mmap of the currently-indexed extent, re-mapped as the file grows. Safe under rotation on POSIX: `rename`/`unlink` leave an existing mapping intact (it holds the inode), and copytruncate is caught by the size-shrink check below. No copying, fast random access on the paint path.
- **`BufferedLogSource`** (Windows, and the fallback everywhere) — incremental buffered reads. Preferred on Windows because a held file mapping can block the writer from rotating or truncating the file — exactly what a logging framework does — and under the always-watched model that risk would otherwise apply to *every* open file, not just ones a user chose to tail. Opened with full sharing (`FILE_SHARE_READ | WRITE | DELETE`) so loftail never locks the writer out.

  **That sharing is `SharedReadFile`, a hand-written open, and `QFile` is what it replaced.** `QFile` reads a growing file correctly on both platforms, but its Windows open passes `FILE_SHARE_READ | FILE_SHARE_WRITE` and *not* `FILE_SHARE_DELETE`, so while a tab held a log its writer could not roll or delete it — a sharing violation on precisely the operation this bullet exists to protect, and on precisely the platform this source exists for. Appends were unaffected, which is why it survived six milestones of local green: the operation the read path exercises all day is the one the missing bit does not touch. The seam is one class with two implementations — the Windows `CreateFileW` with all three share bits, `QFile` everywhere else, where an `unlink` or `rename` needs no permission from a reader — and it is the only file in the tree that includes `<windows.h>` on purpose. The source keeps its own `m_path` rather than asking the handle for one, because a handle carries no name and `wasReplaced()`, `originVanished()` and `computeIdentity()` all need one after it is closed.

The `bytes()`/`size()` interface hides which one is in use; the model and indexer are identical across both.

**Rotation/truncation detection is always active** (it is not gated on a tailing toggle any more): poll size and file identity (device + inode from a `stat` on POSIX, volume serial + file index from a handle on Windows — `pathIdentity()`, both in `SharedReadFile.cpp`). If size shrinks or identity changes, the file was rotated — discard the index and rescan. **The identity is re-resolved from the PATH, never read off the open handle**, which is the whole point: a handle follows the file it opened, so it sees a rotation as nothing at all. **0 means unknown and never means replaced** — the path is not there, the file will not open, the volume has no index that fits (ReFS) — and the gap between a roll's rename and its recreate is exactly that case, so reading it as a difference would rescan against a file that does not exist yet. The "was it replaced" half of that question lives behind `LogSource::wasReplaced()`, because *what has to be re-resolved* differs per source: a mapped fd follows the inode it mapped and sees nothing, so it re-stats its path, while a spooled remote source compares generations (§6.3). The controller asks the source and does not care which. `QFileSystemWatcher` is the primary change signal but is unreliable on some filesystems (notably network mounts), so pair it with a low-frequency size poll rather than trusting it alone. On POSIX, guard mmap reads against a concurrent copytruncate so a read past the new EOF cannot `SIGBUS`.

**Size and identity are not enough, and the third case is a rewrite in place.** `cp new.log app.log`, an editor saving over an open log, a service restarting onto the same path: the inode does not move, so `wasReplaced()` is false; the path still resolves, so `originVanished()` is false; and once the new content reaches the old length the size does not shrink either. The tick then reads the growth as an **append**, resumes indexing from the old tail offset, and the pre-rewrite records stay on screen for the rest of the session with the new bytes parsed from the middle of a record. At exactly equal lengths nothing moves at all and the view simply never updates. A rewrite is only ever visible in the **content**, so both local sources carry a `HeadWitness` — a copy of the file's first kilobyte as it stood when the source last agreed with the disk, re-compared on every `refreshSize()`. An append never touches bytes already in the file, which is precisely what makes "the prefix changed" mean *rewritten* rather than *written to*; the residual limit is a rewrite whose first kilobyte is byte-identical to the old one. It is folded into `wasTruncated()` rather than given a predicate of its own, because the caller's response is the same rescan and `LiveController` already treats truncation and replacement as one question. The cost is a `memcmp` of an already-mapped kilobyte per poll — which is why the local check runs unconditionally where the remote one (`SshFetcher::remoteHeadDiffersFromSpool()`, §6.3, the same idea over a network) is fenced to run only on suspicion. It mattered most on **Windows** for as long as `pathIdentity()` was stubbed there and `wasReplaced()` was therefore always false — the content check was the only thing that could tell a rotation from an append at all. Now that the stub is gone the two platforms lean on it equally, and it covers what no identity can: the file that was rewritten is the same file.

Files are opened in binary mode; CRLF is handled explicitly rather than via platform text-mode translation, so a Windows-authored log reads identically on Linux.

### 6.1 Encoding

`SPEC.md` §4 makes encoding an explicit per-file setting whose default is auto-detect. **The stored setting is the user's choice, including the sentinel `Auto`** — not the encoding that detection resolved to. Persisting the resolved value would silently freeze a guess made from one version of a file and apply it to a later one that may differ.

Detection runs on open, over the first ~64 KB:

1. **BOM** — decisive when present: UTF-8, UTF-16LE, UTF-16BE.
2. **No BOM** — a high frequency of NUL bytes at alternating positions indicates UTF-16, and which position identifies the byte order. Otherwise, validate as UTF-8; on failure fall back to the system 8-bit codepage.
3. The resolved encoding is surfaced in the format editor so a wrong guess is visible rather than silent.

Forcing an encoding skips detection entirely. Detection is a heuristic — unreliable on short files, on files whose leading records are pure ASCII, and on legacy 8-bit logs — so the explicit choice is a first-class path, not a fallback.

Changing the encoding invalidates the index and requires a full rescan, since line boundaries themselves depend on it.

The consequence that reaches furthest: **the record scanner cannot search for `\n` bytes.** In UTF-16 a newline is `0A 00` or `00 0A`, and a naive byte search both misses real terminators and fires inside unrelated code units. A `Decoder` sits between `LogSource` and the indexer, exposing line boundaries and decoded text; the indexer works in its terms and never touches raw bytes directly.

`Record::offset` and `length` remain **byte** offsets in all encodings — they index the source, not the decoded text. Only the decoder converts.

### 6.2 Designing for future sources

`FUTURE.md` plans `.gz` and SSH-retrieved logs, and both violate an assumption that is otherwise easy to bake in: **that a log source is local and randomly seekable.** Neither is. Gzip has no random access without an index; a remote source adds latency to every read.

The `isRandomAccess()` flag exists so the indexer can branch now rather than being restructured later. Concretely, the constraint to honor today: **the indexer must be able to work as a forward, single-pass stream.** It already does — it scans start to finish. Do not add a second backward pass or a "seek to offset X and re-read" step. Random access is a legitimate optimization for `data()` on the paint path, which is only reachable for records already indexed and, for non-seekable sources, will be served from a local cache.

**How that turned out (M11).** Half of this prediction was wrong, and the record is worth keeping straight rather than quietly amended. `isRandomAccess()` was expected to go *false* for SSH; it did not, and the flag remains unread by any branch in the codebase. The reason is the last clause above: once a non-seekable source is "served from a local cache", the cache is an ordinary local file and the source is randomly seekable again — the latency the flag was meant to warn about is absorbed by the cache, not exposed through the interface. What did pay off, decisively, is the **forward-single-pass constraint**. Because the indexer never seeks backwards, the spool can be filled and indexed *concurrently*, which is the whole difference between following a remote log and downloading one. Had the indexer needed a second pass, `SpooledLogSource` would have had to block until the fetch completed, and remote logs would not be live. Keep the constraint; treat `isRandomAccess()` as documentation of intent rather than as a working seam.

**And again for `.gz` (M12).** The other half of the prediction was wrong in exactly the same way, which is what makes it worth recording twice rather than once. Gzip really has no random access — and it did not matter, for the identical reason: the expansion lands in a spool, the spool is an ordinary local file, and `isRandomAccess()` stayed true. The forward-single-pass constraint paid a second time, and more visibly than the first: an archived log **fills in as it expands** rather than freezing until it is done, because the spool is being filled and indexed at once. Two features, one constraint, and the flag that was designed for the job is still unread. The lesson to carry forward is that the *cache* was the accommodation, not the flag.

### 6.3 The spool, and remote sources (SSH)

The spool machinery below is **shared by every source that is not already a readable local file** — SSH since M11, archives since M12 (§6.4). It is named for that rather than for the transport: `SourceFetcher`, `SourceSpool`, `SourceSpoolRegistry`. SSH is a *transport* and an archive is a *file type*; the two compose, so a seam serving both must not be named for one of them.

A log is fetched forward into a **local spool file** and read back through an ordinary local source. `SpooledLogSource::bytes()`/`size()` delegate to `openLogSource(spoolPath)` — the same mmap-on-POSIX / buffered-on-Windows source everything else uses. Nothing on the read or paint path knows where the bytes came from, and `isRandomAccess()` stays true (§6.2 explains why that is not the failure it looks like).

**The spool is shared per log and reference-counted**, not owned by a Document. `SourceSpoolRegistry` hands out `shared_ptr<SourceSpool>` keyed by a plain normalized path **string** — the registry holds spools for several kinds of source and understands none of them; only `defaultFetcher()`, which builds the fetcher, has to read the key. The last handle dropping tears down the fetcher, the connection, and the spool files. This is the load-bearing decision, and it is what makes three separate problems not arise:

- `Document::rescan()` runs on the GUI thread from the live watch tick. It reopens with `OpenPolicy::Reuse`, finds the live spool, and returns — a rotation mid-tail is a pointer swap, never a reconnect that could block the UI or prompt for a password behind the user's back.
- Two tabs on one remote file share one connection and one spool.
- Changing a remote file's log format reopens the Document and costs no network.

**Three threads, and the contract between them is the design:**

| Thread | Owns |
| --- | --- |
| GUI | `Document`, `LiveController`, the `SpooledLogSource`, and the inner local source over the spool |
| Index worker (existing) | `Indexer`, reading that same inner source via `bytes()` |
| Fetcher (one per spool) | `SourceFetcher`, the `LIBSSH2_SESSION` or the decompressor, and every write to the spool |

Two rules keep them apart, and there is no mutex between the GUI and the fetcher at all:

1. **`refreshSize()` is the only method that reopens or re-maps the inner source, and exactly one thread ever calls it on a given instance.** This already held for local files — `Indexer::index()` snapshots `size()` once and `LiveController` is constructed only after the worker joins — but it *matters* now, because the fetcher is appending during the initial scan. The rule is stated **per instance**, not as "the GUI thread": for a Document's source that thread is the GUI thread, but a fetcher may hold a private source of its own and drive it from its own thread, which is what §6.4 does and why the distinction is not pedantry.
2. **The fetcher publishes `committedSize` only after its write has landed, and readers clamp to it.** `refreshSize()` returns `min(spoolFileSize, committedSize)`. A half-written chunk is therefore not merely unlikely to be observed, it is unobservable. This ordering is the entire synchronisation.

**Rotation makes a new spool *generation*, never a rewrite.** The index worker may be mmapping the current spool and every `Record::offset` indexes it, so on a rotation or truncation the fetcher opens spool file *N+1* and bumps an atomic generation, publishing it last once the new file exists. `identity()` returns the generation and `wasReplaced()` compares it, so `LiveController`'s existing rotation path works unchanged. The old spool is unlinked when its last reader lets go.

**Detecting rotation without an inode.** SFTP attributes carry size and mtime but no inode. The primary check is `fstat(handle)` against `stat(path)`: OpenSSH's `sftp-server` implements FSTAT against the real descriptor, so an open handle follows the rotated-away file exactly as a POSIX mmap does locally, and a disagreement between the two means the *name* now points somewhere else — including the same-size rotate that a size check misses. Whether a given server behaves that way is probed once at connect; one that re-resolves by name instead falls back to comparing the head of the file, and only on suspicion, never on the ordinary poll. **Suspicion has two spellings**, and which one applies depends on whether the server can report an mtime at all: normally it is *mtime advanced without the size growing*, and on a server measured without `stat` (§6.3.1) there is no mtime, so it is *the size has stalled* — the same compare, paced by a timer instead of by an event.

**Reconnecting (M13).** The tail loop above polls but never re-established a session: `connectTo()` was only ever called from `start()`, so a dropped link stayed dropped until the log was reopened. It now reconnects from the worker, non-interactively, and a `start()` that merely could not reach the host succeeds into `State::Waiting` instead of failing the open. See §6.5.1.

**The socket is taken away from Qt, and it has to be** (`SocketDetach.h`). `QTcpSocket` resolves the name, applies the connect timeout and phrases the connection error — and then its descriptor is duplicated and Qt's own copy closed, so libssh2 is the only reader. Skipping that step does not degrade the transport, it breaks it: a `QTcpSocket` keeps a read notifier armed, so any turn of a Qt event loop drains the socket into a `QByteArray` libssh2 cannot see, and libssh2 waits out its timeout and reports "Timed out waiting on socket". Two ordinary event loops did it — the modal password prompt, which runs one in the middle of authentication (hence: agent and key logins fine, password logins failing the instant the password was accepted), and the main window's own, which runs for the whole life of a tail while the session belongs to a fetcher thread. The keychain's nested `QEventLoop` (§6.3.2) is a third such loop in the same window, and it is safe for the reason already given rather than a new one — the descriptor is gone from Qt before the handshake, let alone before `authenticate()`. It carries `QEventLoop::ExcludeUserInputEvents` to stand in for the modality a bare loop lacks, which is the only thing the dialog had that it does not. `tst_socketdetach` pins the Qt behaviour on a loopback pair, ungated, because the property is Qt's rather than libssh2's and a Qt that stopped doing it would make the workaround unnecessary.

**Connecting happens on the fetcher's own thread (M17).** It did not until M17: the connect, host-key check, authentication and a 128 KB prime all ran on the thread that opened the document, and only the tail loop was handed over. The stated cost was "a frozen UI for the length of a connect, bounded by the SSH timeout" — twenty seconds, per log, and at session restore before the window was shown at all, because `restoreSession()` runs in the `MainWindow` constructor. That was the whole of M17. See §6.3.3.

What survives from the original design is the part that was load-bearing: exactly one thread touches a `LIBSSH2_SESSION` at a time. It is now the fetcher's own thread from the first byte rather than after a handoff, which is a stronger version of the same rule. The follow-up that paragraph named — "a 'Connecting…' dialog with Cancel … needs the connect moved off-thread to be worth having" — is now possible; what shipped instead is a waiting tab that says `connecting…` and can simply be closed, which needs no dialog.

**One prompt per host** comes from a per-target credential cache, not from a shared connection. Sharing one `LIBSSH2_SESSION` across the per-file fetcher threads would need a mutex around every read and would serialize them; caching the accepted password per `user@host:port` gets the user-visible property with none of that. The cost is one TCP connection per open file, which is what `scp` does anyway.

Since M17 the cache needs help to deliver that. It used to be enough on its own only because every connect ran on the GUI thread and they were therefore serialised by construction: the first file prompted and cached, the rest found it. With each fetcher connecting on its own thread, five files on one host reach authentication together, all miss the still-empty cache, and all ask — five stacked dialogs, and five of sshd's six default `MaxAuthTries` spent producing them. `SshConnectHold` serialises the connect **per target**, held across authentication so the waiters find the password rather than ask for it; different hosts still connect in parallel, which is where the time is actually saved. Coalescing the prompts themselves would be wrong — keyboard-interactive is a conversation whose wording differs per prompt, so one host's answer is not in general another's question.

**The full ladder `authenticate()` climbs**, in order: the agent and the `~/.ssh` default keys; the per-target credential cache above; the OS keychain (§6.3.2); and only then the prompt, up to three times. A **saved host's** remembered plain-text password enters at the *cache* rung rather than as a rung of its own — the UI primes the cache before the open (`MainWindow::primeRemoteCredentials`) — which is what keeps the agent ahead of it: a host that would have signed in with a key never has a stored password sent for it. Note what this costs: sshd counts failures against `MaxAuthTries` (6 by default), and the keychain rung moves the worst case one attempt closer to that ceiling, which is why a stored password the server rejects is *erased* rather than left to fail again on every future connect.

**Rotation detection is a ladder, and its verdict is a pure function.** `rotationVerdict()` lives in `SshExecCommands.h` — **ungated and always compiled**, for exactly the reason `shellQuote()` and the size ladder are: it is the only judgement the remote transport makes on its own, and a rule compiled in one configuration is a rule tested in one configuration. `tst_sshexec` drives it with no server, no socket and no libssh2. It returns one of four answers, and the fourth is what the poll costs:

| Verdict | When | What the poll does |
| --- | --- | --- |
| `Rotated` | it shrank below what we read, or the handle and the name disagree on size | reopen and re-prime, no read spent |
| `CompareNow` | the mtime moved and the size did not | read the head at once |
| `ComparePaced` | **it grew**, or the server has no mtime at all | read the head only if `stallProbeDue()` allows |
| `Nothing` | nothing moved | nothing |

**`ComparePaced` on growth is the M12-era hole this closed.** A rewrite in place on the far end — `cp bigger.log app.log`, a service restarting onto the same path — moves neither the inode nor the size below what has been consumed, and **on the SFTP rung the handle and the name still agree, because they are still the same file**; only the content moved. A working `sftp-server` FSTAT is no help against it whatever. So growth cannot be treated as evidence of an append on *any* rung, and the local sources' head witness (§6) has a remote counterpart in `remoteHeadDiffersFromSpool()`. What differs is the fence, and only the fence: the local check is a `memcmp` of an already-mapped kilobyte and runs on every tick, while this one is a 4 KB read over somebody else's link and is therefore paced — at most one every `kStallProbeMs`, a single budget shared with the no-mtime rung, so a bursty log alternating growth and stall still costs one read per window rather than one per poll. The user-visible cost is that a remote rewrite-that-grows may take up to half a minute to be noticed, which `SPEC.md` §3 states outright rather than leaving to be discovered. Reducing that means asking the server about a log that is almost certainly just being appended to, which is invariant #5's whole subject.

**The transport sits behind `SourceFetcher`**, and that seam is what makes the feature testable: `tst_spooledsource`, `tst_remotetail` and `tst_remoteopen` drive the whole application — opening, indexing, tailing, rotation, session restore — against a fake fetcher, with no network and no libssh2 linked. CI exercises no libssh2 call beyond linking; the handshake, host-key and authentication paths are covered by `tst_sshlive`, which runs by hand against a real server.

#### 6.3.1 The exec fallback, for a server that will not do SFTP

Some servers sign you in and then refuse SFTP — sshd with no `Subsystem sftp` line, or an account confined to a shell that cannot start one. Before this, that was where a remote log stopped. `SshSession` now has two modes, chosen at connect: SFTP, and failing that, ordinary shell commands over a plain exec channel. `SshFetcher` and everything above it are unchanged, because the five operations they use (`openFile`, `statPath`, `statHandle`, `readAt`, `fstatTracksHandle`) are the same five either way.

**Reading and measuring are two different questions, and only the first has one answer** (M16). Reading is `tail -c +N | head -c L` and there is no substitute for it. Measuring was `stat`, and `stat` is exactly what a stripped-down embedded image leaves out — the same image whose sshd accepts an SFTP subsystem request with no `sftp-server` behind it, so the two failures arrive together on the same machines. Insisting on `stat` therefore refused the log on the very boxes the fallback was built for, and told the user to install something they often cannot. So measuring is a **ladder**, settled per server:

| Rung | Command | Cost | mtime |
| --- | --- | --- | --- |
| `Stat` | `stat -c '%s %Y'` ‖ `stat -f '%z %m'` | O(1) | yes |
| `Ls` | `ls -lnLd` | O(1) | no |
| `Wc` | `wc -c <` | **O(file size), every poll** | no |

`Ls` is where practically every no-`stat` box lands, because `ls` exists on every POSIX userland that has a shell at all. `Wc` is an exactness backstop for an `ls` output shape nobody anticipated, and it is **fenced rather than merely disclosed**: it will not settle on a file over 8 MB, the poll interval is clamped to 15 s while it is in use, and past 64 MB the fetcher reports an error naming the remedy. The default poll is once a second, and "re-read the whole log every second on the machine being observed" is not a cost to put in the status bar — it is invariant #5, and a note is not a substitute for not doing it. (`tail -c +floor | wc -c` was considered: O(delta) and exact, and **blind to truncation**, because a copytruncate leaves `floor` stale, the `size < consumed` rotation test never fires, and the new file gets read at the old file's offsets. Silently garbled output is worse than a slow poll.)

Every flag in `ls -lnLd` is load-bearing and dropping one is a silent bug. `-d` stops a directory operand listing its *contents*, which the last-non-empty-line rule would then take for the answer. `-L` dereferences, so a log reached through a symlink reports the target rather than the length of the target's *path*; POSIX is explicit that `-L` beats `-d`, and busybox, GNU and BSD all comply. `-n` keeps user and group numeric, so a user name containing a space cannot shift the columns. `LC_ALL=C BLOCK_SIZE=1 LS_BLOCK_SIZE=1 QUOTING_STYLE=literal` in front defeats a remote `/etc/profile` that would otherwise print `1.0M` where a byte count is expected; unknown variables are ignored everywhere else, so it costs nothing. And the requirement that the type character be `-` is what rejects a directory, a dangling symlink, a FIFO — and a device, whose size column is not a byte count at all but a `1, 3` major/minor pair that would shift every field after it. One case the parser cannot defend against is closed by declining the rung instead: a filename containing a **newline** can carry a complete, plausible `ls` line of its own and choose the size loftail believes, so a path with a newline in it skips `Ls` entirely. The other two rungs print no filename, so neither is exposed.

**A settled rung is proved before it is believed, and the proof is about the read path.** `ExecSizeProbe::settle()` accepts a size only after `readAt(size - 1, 1)` delivers a byte — which runs the real `readCommand()` end to end and is the only thing anywhere that establishes **`head -c` works on this box**. That matters more than it sounds: `head -c` is *not* POSIX (POSIX `head` has only `-n`), so `command -v head` succeeding says nothing about it, and a `head` without `-c` prints a usage error to stderr and no bytes at all. Before this, such a box passed the probe, opened the log, and returned zero bytes from every read — which is precisely what EOF looks like, so the tab opened empty and never said why. Two rules keep the proof from being flaky on the thing it is used on, a log that is being written to:

- **Only over-reporting is detectable, and only over-reporting is harmful.** The file grows between the size query and the read, so a size that came back too *small* is indistinguishable from growth — and costs one poll of latency, nothing more. A size past the end returns nothing, and that is the one answer worth refusing.
- **A size of zero is believed without a read.** There is no byte to prove anything with, and a log that exists and is empty is an ordinary thing to open.

Two further rules about *when* it settles, both of which look like optimisations to undo and are not. The ladder runs **before** the existence check rather than after, because `statPath()` has nothing to dispatch on until a rung is chosen — and that is not a compromise, since "no rung answered" and "the file is not there" are the same observation from out here and want the same answer. And it re-settles on **every** `openFile()`, which means on every rotation: settling once per session would let a rotated-to file that the chosen rung cannot parse make `statPath()` invalid for good, and the fetcher would then report the log as waiting on every poll, indistinguishable from one that was deleted.

**The fallback is chosen by probing, never by reading the error code**, and that is the correction that made it work on the machines it was written for. "No SFTP" arrives in two shapes and libssh2 reports them differently for reasons that have nothing to do with which one it is. A server that *answers* the subsystem request with a refusal gives a prompt channel failure. A server that **accepts** the channel and then has no `sftp-server` binary behind it — a generic sshd config on a stripped-down embedded image, which is the common case — gives libssh2 nothing at all to report: it waits for the SFTP version packet that is never coming and gives up with a plain `LIBSSH2_ERROR_TIMEOUT`, "Timed out waiting on socket", *after a successful login*. Classifying a timeout as "transient, retry as you are" therefore locked out exactly the servers the fallback exists for. So the code is not consulted for that decision at all: run the probe command, and if a command runs then the session is healthy and it is SFTP that is missing, whatever the error said. The code is consulted only afterwards, and only for the one question the caller actually asks — if the probe went unanswered too, a timeout means the link went quiet (retryable, `Unreachable`) and anything else means the server answered and said no (`Refused`).

Two details of that probe. It runs on a **shorter leash** when the SFTP attempt timed out — a session that has just been silent for the whole window has already cost the user that wait once, and doubling it would tell them nothing they do not already know — the leash is now about how long a tab spends saying "connecting…" rather than how long the window is frozen, but the reasoning and the number are unchanged. And its failure is reported in **three** ways rather than one, because the two questions above are separable and `runCommand()` distinguishes its own two outcomes for free: a command that could not be started at all means the account has no shell; a command that ran and printed no marker means the shell is fine and `tail`/`head` are missing; and a marker with no tool named after it means the log can be *read* but not *measured*, which is the smallest remedy of the three and deserves to be said on its own — any one of `stat`, `ls` or `wc` is enough.

The probe answers both questions in **one line**, marker first, then whichever of the three size tools exist. One line because every answer the exec transport reads is taken from the last non-empty one, and a multi-line reply would defeat that; marker first so the parse has a fixed head to anchor on. Names it does not recognise are ignored rather than fatal, so an older loftail and a newer probe do not refuse each other.

Two-way return values matter here in a way that is easy to flatten. `ExecSizeProbe`'s command seam returns "ran / did not run" separately from what was printed, exactly as `Impl::runCommand` does, because **a dead channel is not a missing file**: one is reconnected and the other is waited for, and collapsing them makes a dropped link read as a log that has not been written yet — forever, since nothing then reconnects.

**SCP was considered and is not usable**, which is worth recording because it is the obvious suggestion. The transport needs to read from an arbitrary offset, re-`stat` the path on every poll, and `fstat` an open handle to tell a same-size rotate from an append. SCP offers none of the three: it hands over a whole file from byte 0, with its size fixed at open and no handle to interrogate. An SCP-backed tail would re-download the entire log on every poll. `tail -c +N` gives genuine forward reads, which is the one property the single-forward-pass indexer actually needs (invariant #9).

The fallback is **automatic and silent**. It is only reached once SFTP has already refused, so there is nothing to lose by trying it, and a tail that is keeping up is the ordinary case whatever transport carries it. There was a `FetchStatus::note` here that put a standing remark in the status bar naming the mode and the rung; it is gone, because a line that never changes and never clears is read once and ignored thereafter, and it occupied the one slot the status bar has for saying something that *is* urgent. The costs below are real, but each is either invisible while the tail works or already reports itself: the `Wc` ceiling raises an ordinary `State::Error` naming its remedy, and a link that dies becomes `State::Disconnected`. Four costs come with the mode, then, and none is *hidden* — but none announces itself either:

- **A process per read.** Every `readAt` is a channel plus a `tail | head` on the far end, where SFTP reuses one handle. Chunked at 256 KB, so a prime is round-trip-bound rather than pathological.
- **Weaker rotation detection.** There is no handle, so `statHandle()` deliberately reports *invalid* rather than quietly returning the path's attributes — which would make the two agree by construction and defeat the very check that compares them. `fstatTracksHandle()` is false, and `SshFetcher`'s existing mtime/head-compare fallback (§6.3) is what runs.
- **Weaker still with no mtime**, on the `Ls` and `Wc` rungs. "It changed without growing" cannot be asked when nothing reports *when*, so the suspicion becomes a **stalled size**, and since a stalled size is also exactly what an idle log looks like, the compare is paced by the clock: at most one 4 KB read every 30 s. Two consequences worth stating rather than discovering. A rotation is noticed within half a minute rather than at once. And a *finished* log — one nobody is writing to — pays that 4 KB read every 30 s for the life of the tab, which is the irreducible price of having no mtime. A growing log pays nothing, because the size test is false while it grows; the timer is therefore restarted only when a compare actually runs, and deliberately **not** reset on growth, since a bursty log alternates growing and stalling and resetting on growth would fire the compare every other poll.
- **A shell, and therefore quoting.** The remote path reaches a command line, so `shellQuote()` is a security boundary rather than a formatting detail: a path containing `'; rm -rf ~; '` is otherwise remote code execution. Single quotes, with the one escape POSIX allows (`'\''`).

`SshExecCommands` — the quoting, the command construction and the parsing of what comes back — and `ExecSizeProbe` — the ladder and its proof — are **always compiled**, like `RemoteLocation` and `ArchiveLocation`, while the transport that uses them is gated. A security boundary compiled in one configuration is a security boundary tested in one configuration, and the same goes for the only decision the transport makes: reaching `SshSession`'s exec branches needs libssh2, a server with no working SFTP, and — for the rungs below `stat` — a server missing a utility every developer machine has. `tst_sshexec` and `tst_execsizeprobe` are both ungated. The first runs the generated commands through a real `/bin/sh` against real files, with a canary file the injection cases must fail to create; comparing strings would only prove the quoting matches what the author expected, not that a shell agrees. The second injects the command and read seams, so the whole ladder — including a rung that over-reports, a size that went stale while the log grew, an empty file, a read path that delivers nothing, and a dead channel — runs against real files with no network and no libssh2 linked.

Parsing is defensive for the same reason the classification in §6.5 is: a wrong size here would truncate or over-read a log, so anything that is not exactly the expected shape reads as "no attributes" — two non-negative integers from `stat`, one from `wc`, and from `ls` a nine-field line whose type character is `-` and whose link count, uid and gid are all numeric. The answer is taken from the **last** non-empty line, because a login banner on stdout is common and is somebody else's noise.

One command-construction trap, because it bit this file and would bite it again. `readCommand()` builds its string with a **single** three-argument `arg()` call. Chaining `arg()` is wrong: the second call rescans the whole string including the path the first one just substituted in, so a path containing a literal `%1` — legal, and what a URL-decoded `%251` arrives as — had that marker replaced by the length. Not an injection (`arg` on a number inserts digits only), just the wrong file. And the obvious `.arg(from, quoted, length)` with the numbers left as integers binds to `arg(qlonglong, int fieldWidth, int base)` and means something else entirely, so they are converted by hand.

#### 6.3.2 Where a remembered password lives (M14)

A password the user asks loftail to **keep** goes through one seam, `SecretStore` — abstract, in `loftail_core`, free of QtKeychain types and **always compiled**, with a global setter in the shape `SshPrompter` established. Only `KeychainSecretStore.cpp` includes QtKeychain, and only when `LOFTAIL_HAVE_KEYCHAIN` is set; `SecretStore.cpp` picks it or a `NullSecretStore` at the call site, exactly as `SourceSpool::defaultFetcher()` does for `makeSshFetcher`.

**`secretStore()` is never null, and `sshPrompter()` may be.** That is the one deliberate divergence between the two. For a prompter, null *is* a policy — "never prompt", and every question then answers itself in the safe direction. Here "no keychain" is not a policy, only which backend was compiled in or found at runtime, and it already has a first-class spelling the object gives about itself: `available() == false`. A nullable store would put a null check at every call site guarding a condition the store already states.

**`available()` is a round trip, not a link check.** QtKeychain's own `QKeychain::isAvailable()` answers "was a backend library found", which on Linux is true as soon as `libsecret-1` can be `dlopen`ed, running daemon or not — upstream says so in `keychain_unix.cpp`: *"In the future there should be a difference between 'API available' and 'keychain available'."* A headless CI runner and a KDE box with `kwalletd` not started are the same case and both pass that test. So it is used only as a cheap negative, and a real read of a probe key decides — where **`EntryNotFound` is the probe's success**, because only something that is there can say so. Two consequences worth stating rather than discovering: the answer is cached for the process, so a keyring started after loftail is not noticed until restart (the alternative is a D-Bus round trip on every connect and every dialog build); and inside the AppImage `available()` is false on a host with no `libsecret-1.so.0`, because QtKeychain reaches libsecret through `QLibrary("secret-1")` and `ldd` therefore cannot see it for `linuxdeploy` to bundle.

**The consent rule.** `rememberSshPassword()` returns `UseFileFallback` only when `available()` said no. It never returns it after `available()` said yes: a keychain that is present and refuses yields `Failed`, and the caller reports that and writes nothing. The rule exists because the checkbox names its destination *before* it can be ticked, so a silent downgrade would put a secret in a file the user was never told about, from the one dialog whose whole job is to say where the secret goes. It is an executable assertion in three places — `tst_secretstore`, `tst_hostbookmarks` and `tst_sshcredentials` — all ungated, because it is a rule about consent rather than about a dependency.

**The consent line is shown in every sign-in mode, including the one with nothing to consent to.** The Open Remote dialog used to hide it whenever an agent or a key was selected, reasoning that a warning firing when nothing is at stake teaches people to read past the ones that matter. That reasoning is right about *warnings* and was being applied to a *row*: the row answers "where would a remembered password go", and with an agent the answer is "nowhere", which is worth saying and is not a warning. It now says exactly that, in muted text with no ⚠, and only the plain-text case is styled as a caution. What hiding it cost was that the dialog changed height by some eighty pixels, under the pointer, every time the sign-in combo changed — so the row's height is reserved for the longest of the three wordings and the dialog is now the same size in every state. The label also **spans both form columns**: in the field column a word-wrapped `QLabel` was allotted a fraction of the dialog's width and broke the `hosts.json` path across three lines mid-token, which is a poor way to satisfy a rule whose entire content is *name the file*.

**`SshSession` does not decide where a password goes**, because it does not know what the user was shown. `SshPrompter::passwordAccepted(target, password, remember)` is called once, only after the server's yes, and the prompter routes it — the object that drew the checkbox is the only one that knows what was consented to. This is also what finally consumes the `remember` out-parameter, which the dialog had been filling in and `authenticate()` dropping since M11.

**The thread rule: a keychain is consulted only on the thread that has a prompter.** Three reasons, the first sufficient alone. (1) A keychain read can *prompt* — non-interactive under `CredRead`, but a locked KWallet raises `kwalletd`'s unlock dialog and macOS asks for an item whose ACL does not list the binary; `SshFetcher::reconnect()` already forbids exactly that, in those words. (2) The fetcher's worker runs no event loop — `Worker::run()` is `tailLoop()`, with no `exec()` — while QtKeychain's Unix path wants `QDBusConnection::sessionBus()`. (3) `reconnect()` needs none of it anyway: the password went into the credential cache when the document was opened, a rung earlier. Enforced twice — structurally, by putting the keychain rung *below* `authenticate()`'s existing "is there anybody to ask" test, and at runtime by a thread guard in `KeychainSecretStore`, so a later caller cannot quietly reintroduce a keychain read on the fetcher thread.

**M17 marshals the read rather than moving the rung**, and the distinction matters. Every keychain call now runs on the application thread whoever asks, because `secretStore()` hands back a marshalling view rather than the installed store (§6.3.3) — reason (2) is answered structurally, and no caller has to remember. Reason (1) is not answered by that and must not be thought to be: the "is there anybody to ask" test is about whether a **person** is there, not which thread is running, and an unattended retry — which passes no prompter — must still never raise an unlock dialog for a log the user opened hours ago. The rung stays where it is. A latent bug in the runtime guard was fixed at the same time: `available()` latched its probed flag *before* the thread check, so one off-thread call turned the keychain off for the rest of the process, and M14's remembered passwords would have stopped working with every test above this seam still green.

**Nothing in CI exercises a real keychain**, and nothing can: the runners are headless with no session bus, so no backend would answer. `tst_keychainlive` is gated twice like `tst_sshlive` — not built without the dependency, and skipped unless `LOFTAIL_TEST_KEYCHAIN` is set, because it writes to the developer's real keyring. Everything above the backend is covered with no keychain at all through `tests/FakeSecretStore.h`. A green pipeline says nothing about KWallet, GNOME Keyring, the Credential Manager or the macOS Keychain.

**The plain-text file is unchanged**, in shape, schema and containment rules, and remains the fallback where no keychain will answer — `HostBookmark::savePassword` and `password` in `hosts.json` (§8), off by default, owner-only, named in the dialog. `forgetSshPassword()` deliberately touches **only the keychain**: clearing the file from inside a network auth routine would mean `SshSession` reading `AppConfigLocation`, the hidden dependency the bookmark lookup was kept out of core to avoid. That asymmetry is the price of the placement, and a stale plain-text entry is cleared where it was set.

#### 6.3.3 Opening without blocking (M17)

Opening a remote log froze the window for as long as the far end took, and at session restore it froze it before there was a window: `restoreSession()` runs in the `MainWindow` constructor, which is `main.cpp` line 108 — `show()` is line 109 and `exec()` is line 118. A session with three remote tabs on a host that was down showed nothing at all for a minute. `SourceFetcher::start()` is now **non-blocking by contract**, for both fetchers.

**The waiting state was already there.** M13 built "a tab that exists with no bytes and fills in later" for a log that has not been written yet, and a not-yet-connected spool is the same situation one step earlier. `LogSource::notReadyYet()` is the predicate that says so — true for a spool with nothing committed and a state of `Idle`, `Connecting`, `Priming` or `Error`. Almost nothing else changed; the document, the live seam, the `◦` tab and the placeholder are M13's, untouched.

Three rules in that predicate are load-bearing and all three read as safe to tidy away.

- **It is asked on BYTES, never on a state change.** `Document::resume()` is a one-way door: it clears the waiting flag unconditionally, and opening a spool never fails, so a resume with nothing to read settles the format against an empty sample, leaves `m_formatSettled` false for ever, and takes the document out of the only state from which the settling path is reachable. Autodetect, the format dialog and format persistence all stop working, silently.
- **`Live` is excluded**, so an empty remote log opens as an ordinary empty tab like an empty local file. Including it would put a `◦` on a log that has demonstrably been found and read — the exact distinction that mark exists to draw.
- **It is consulted in exactly two places** — `Document::prepare()` and `LiveController::checkWhileWaiting()` — and never in `checkNow()`'s vanish branch. Merging it with `originVanished()` there blanks the view on every slow-link rotation: after `wasReplaced()` rescans onto the new generation, the next tick finds `Priming` with nothing committed, and the two-second vanish grace expires on a log that is fine. `tst_remotetail` pins it.

**The prime is published all at once.** The first `committedSize` a fetcher publishes must be the whole format prime or the whole stream. A document settles its format *and* its encoding from the first committed bytes, once and for good — and both libssh2 and libarchive may return short reads, so a per-chunk publish during the prime would settle a log's format against whatever the first read happened to return. After the prime, per-chunk publishing is the point: that is what makes records appear as they arrive.

**Nothing joins a fetcher.** `~SourceSpool` used to call `stop()`, which joined the worker before removing the directory it was writing into — on the GUI thread, every time the last tab on a log closed, with the worker possibly twenty seconds into a connect. `requestStop()`/`isStopped()` replace it, and `SourceSpoolRegistry::retire()` takes the fetcher and its directory and buries them when the thread actually exits. A **timer**, not `QThread::finished`: "a mutex-guarded snapshot, polled, never a signal" is this layer's whole synchronisation model, and one queued connection here is the precedent for the next. `shutdown()` has no event loop left to reap with, so it drains by hand with a two-second cap and then abandons the stragglers — leaking the object rather than joining a thread that will not stop, and leaving its directory for the next launch's sweep, which is granted any instance directory whose lock file is gone.

That cap is only meaningful if a connect can be given up on, which needs two things: the TCP connect waits in 250 ms slices against a stop predicate (**before** the detach — `waitForConnected` runs Qt's machinery on the socket, which is exactly what must stop once SSH bytes move), and `SshSession::abort()` shuts the detached descriptor down from another thread so a blocking libssh2 call returns. Shutdown rather than close, so no descriptor number is freed while another thread is inside libssh2 holding it; the fd is the one member of `Impl` behind a mutex for that reason.

**A question travels to the application thread; the auth ladder does not move.** A prompt is a modal dialog and a keychain read wants an event loop and a session bus, and neither can be restructured into fail-ask-retry, because keyboard-interactive authentication is a conversation libssh2 drives through a callback with the server's own wording per prompt. So `GuiCallGate` carries the call across and brings the answer back, with `PromptRelay` and a marshalling `SecretStore` on top. **One gate for the process**, which makes "one question at a time" true by construction rather than by agreement — two fetchers connecting at once cannot stack two modal dialogs. The discipline lives in `GuiCallGate.h` and nowhere else: the mutex is never held across the work or across a wait; a call is a `shared_ptr` owned by both sides, so a cancelled asker cannot be written into after it returns; a caller must not hold its own locks; and with no `QCoreApplication` the work runs inline, since there is no other thread "the application thread" could mean and the hang being avoided is posting to a queue nobody drains. Cancelling refuses every pending and future call and wakes every waiter, which is what stops a fetcher asked to stop from holding up its own teardown — and `setSshPrompter(nullptr)` cancels, because "null means never prompt" has to reach the questions already in flight too.

**Listing an archive's members** is the same problem without a fetcher: no index, so enumerating a compressed tar costs what expanding it costs. It runs on a worker owning its own `LogSource`, with a cancellable progress dialog in front. It still pumps events from the calling frame rather than returning and continuing later — the user asked to open an archive and must pick a member before anything can happen — but the window repaints, the listing can be cancelled, and every other tab goes on tailing. It is waited for by **polling**, not by quitting a nested `QEventLoop` on `finished()`: `QProgressDialog::setValue()` calls `processEvents()` for a modal dialog, so a quick listing can have its queued `quit()` delivered before `exec()` has begun, and `quit()` on a loop that is not running does nothing.

**What CI can and cannot show.** `tst_asyncconnect` is the test that pins the milestone, and it needs a transport that genuinely takes a second: `tests/FakeFetcher.h` returns from `start()` instantly, which satisfies the old contract exactly as well as the new one. Everything else — the states a connecting spool passes through, the refusal that keeps its tab, the format dialog deferred to the first resume — is driven through the fake, network-free.

### 6.4 Archived sources (M12)

A compressed or archived log is a **second fetcher behind the same spool**, exactly as `FUTURE.md` predicted from the beginning. `ArchiveFetcher` decompresses one member forward into a spool file; `SpooledLogSource` reads it back. Nothing above the fetcher changed.

**The input is an ordinary `LogSource`, and that is the whole design.** `ArchiveFetcher` holds a private `std::unique_ptr<LogSource>` over the container and feeds libarchive from it through a read callback. For a local container that is a `MappedLogSource`; for one on another machine it is a `SpooledLogSource` over the SSH fetcher's own spool — and the archive fetcher cannot tell. So **two fetchers chain**: SSH downloads `app.log.1.gz` while the archive fetcher expands what has arrived. Neither knows the other exists. This is why an archive is spelled as a *nested path* with no scheme of its own (§6.4.1): an archive is a file type and SSH is a way of reaching a file, and inventing `archive+ssh://` would have been inventing a combinatorial problem that does not exist.

Two consequences that are easy to get wrong, and were:

- **A container is opened as bytes, never as a log.** `openContainerSource()` exists beside `openLogSource()` and deliberately skips the archive branch. Without it, `openLogSource("app.log.gz")` — which *means* "expand it" — is what a fetcher would call to read its own input, and it recurses into expanding itself.
- **Spool keys are namespaced by what fills them.** Because a single-stream container collapses to its own plain path (§6.4.1), the expanded log and the raw container are the *same address string*. Sharing a registry key between them is not merely ambiguous: the expansion's own input lookup resolves to the expansion itself — an archive fetcher whose input is its own spool, waiting for bytes only it could produce. (Before M17 the same collision read differently: the registry published its entry only after `start()` returned, so the inner lookup missed the outer spool and built a second expansion, forever. `start()` no longer blocks, so the inner lookup now *finds* the outer one. The prefix prevents either reading.) `expandedSpoolKey()` prefixes the key, and the prefix never escapes the registry.

#### 6.4.1 Addressing

An archived log is spelled by continuing the path through the container: `/logs/bundle.tar.gz/var/log/app.log`, and `ssh://host/logs/bundle.tar.gz/app.log` for one on another machine. Like an `ssh://` URL it travels through the application as an ordinary path **string**, which is again why no session schema bump was needed.

Resolution is deterministic and costs at most one `stat`:

0. A **local path that already names a regular file is never split.** This is what keeps a real directory called `bundle.zip` working — the file that is actually there wins over the reading where the directory is an archive. It cannot apply remotely, where the answer would cost a round trip on a path that is normalized constantly.
1. Otherwise the cut falls at the **first component carrying an archive extension**, of either kind. Which table matched decides what the address *means*; it does not decide where it splits.
2. Otherwise this is an ordinary log.

Classification is **pure string work — no I/O, no content sniffing** — so it answers the same for a file that does not exist yet, which is what session restore needs. The cost is real and is stated in `SPEC.md`: a `.log` that is secretly gzip fails with a decompression error rather than being rescued by a sniff. That is the deliberate trade for determinism.

**The collapse rule.** A single-stream container (`.gz .xz .bz2 .zst`) keeps its **plain path** as the normal form and never grows a member. Without it one log would have two spellings, and therefore two tabs, two format-cache entries and two spools. A multi-member container always carries its member.

#### 6.4.2 Completion

An expansion genuinely ends, and loftail knows it does **because loftail produced the bytes**. That is the one thing invariant #5 does not forbid: the ban is on *guessing* that a file somebody else is writing has stopped.

- `FetchStatus::State::Complete` is published **after** the final `committedSize` — the same ordering rule `generation` follows, so a reader that observes Complete is guaranteed to observe the final size.
- `LogSource::isComplete()` is non-pure and false by default, arriving by exactly the route `wasReplaced()` did in M11: only a source that can prove it implements it.
- `LiveController` reads it **before** `refreshSize()` and acts on it **after** `ingestAppended()`, then stops the watcher for good. Reversing either half drops the last chunk silently — no error, just records that never appear. `tst_complete` pins it, ungated, because it is a contract of the live seam and not of libarchive.

**No user-facing mode follows.** The follow control is untouched; after completion the newest record simply stops moving, exactly as it does for a local file nobody is writing. Stopping the watch is an absence of work, not a setting.

**A cancel is not an outcome, and the check for it goes *after* the read, not only before it.** `ArchiveFetcher::expand()`'s read is the only place the worker blocks — `awaitInput()` parks inside it waiting for container bytes, and `requestStop()` is what wakes it. When it does, the input ends under libarchive, which reports whatever a truncated container looks like in that format: `truncated gzip input` for gzip, a clean end of stream for a codec that cannot tell the difference. Read either as an outcome and the user's own cancel comes back as a **corrupt archive** (`setError`) or, worse, as a **finished** one — `publishComplete()` would overwrite the `Disconnected` that `requestStop()` had just published and tell the live controller that a cut-short expansion is the whole member, which is the one thing completion is supposed to mean (invariant #5). The loop already tested `stopping()` at the top, and that is not enough: the stop is raised *while* the read is in progress, so the check at the top was made before there was anything to see. `SPEC.md` §3's "scanning can be cancelled, leaving whatever was scanned so far usable" is the promise this keeps.

An expansion whose container is remote **does** complete, once the container has been fetched whole. The cautious-looking alternative — never completing, because the container might grow — is not caution but a permanent wait: an SSH fetcher tails forever and never reaches a terminal state, while libarchive always reads past a gzip member looking for a concatenated one. A rewritten container is not re-expanded either way (reopening does that, and rotation is the transport's business one level down), so there is genuinely nothing left to wait for.

#### 6.4.3 Gating and testing

libarchive is optional and auto-detected, gated as libssh2 is (§1): `LOFTAIL_WITH_ARCHIVE`, a three-tier probe, and a configure-time `Archived log sources: ENABLED/DISABLED` line. **One deliberate difference from libssh2: there is no build-from-source fallback.** libarchive is only useful with its codecs, and it finds zlib and liblzma through `find_package` in MODULE mode, which `CMAKE_FIND_PACKAGE_REDIRECTS_DIR` cannot satisfy — a FetchContent-built codec is ignored, libarchive builds with no compression, and reports itself found regardless. That was tried, and it reached CI reporting `ENABLED` while every `.gz` fixture failed to *write*, with zip silently falling back to "store". A package manager supplies the codecs as a matter of course, so the Windows job uses vcpkg; a static libarchive also needs `LOFTAIL_ARCHIVE_STATIC=ON` for the `dllimport` declaration. `ArchiveLocation`, `ArchiveFetcher.h` and `ArchiveReader.h` are always compiled so both builds agree about what a settings file means; only `ArchiveReader.cpp` and `ArchiveFetcher.cpp` touch the dependency.

**Unlike M11, this really is exercised in CI.** There is no network, no credential and no disposable remote path to arrange: the fixtures are built at runtime by libarchive's own write side. `tst_archivelocation` and `tst_complete` run in every configuration; `tst_archivemembers`, `tst_archivefetcher`, `tst_archivetail` and `tst_archiveopen` run wherever the dependency is present. The M11 caveat — that a green pipeline says nothing about the transport — does not carry over to this milestone.

**A test that needs an expansion caught in flight must arrange it, never race for it.** Expanding a *local* container is pure CPU and page cache: `logBody(200000)` — 12 MB, chosen to be far too big to finish at once — expands end to end in about **6 ms**, which is under one Windows scheduler tick. `tst_archivefetcher::aStoppedExpansionKeepsWhatItWrote` used to wait for the prime with a 5 ms poll and then stop, which is not a test of stopping but a bet that the poll after the sleep lands inside those few milliseconds; it held on Linux by about a millisecond and CI eventually collected on it, as a Windows-only failure that looked for all the world like a toolchain change. The fix is to make the precondition true by construction rather than to enlarge the fixture until the race is merely unlikely: the container arrives from a `FakeRemoteFarm` with its tail outstanding (`setTotalSize` past what has been delivered), so the expansion parks in `awaitInput()` and *cannot* have finished, on any machine at any speed. Only the transport is fake; the archive fetcher is the real one.

**Spool files** live under `QStandardPaths::CacheLocation` (never config — they can be gigabytes), in a per-process directory holding a `QLockFile`. Startup sweeps sibling directories and removes only those whose lock can be taken, since a lock that cannot be taken means a live owner — several instances may run at once (`SPEC.md` §3), so "old" would not be a safe test.

**libssh2 is optional.** §1 promises the reference build works with the stock Ubuntu toolchain and nothing separately installed, so it is detected and never required: without it, `RemoteLocation`, the spool, the source and the bookmark store still compile, remote paths are still recognised, persisted and displayed identically, and opening one reports that support is not built in. Only `SshSession.cpp` and `SshFetcher.cpp` are conditional.

### 6.5 A log that is not there (M13)

`SPEC.md` §3 makes an address that is not currently openable a **state** rather than an error: the tab opens, says it is waiting, and starts reading when the log turns up. The same state covers a log deleted while open. It is the third consequence of the same refusal that produced the always-watched model — loftail cannot know whether a log is finished, and it equally cannot know whether one is *late*.

**Waiting lives on the live seam, not in a fourth `LogSource`.** The tempting shape was an `AbsentLogSource` that reports size 0 and turns into a real source when the path appears. It was rejected because the thing that has to change is not how bytes are read — it is *whether there are any yet*, which is the live controller's existing question. A document therefore has three states, and the transitions all happen on the 750 ms tick that was already there:

| State | Source | Index |
| --- | --- | --- |
| Open | yes | the log |
| Waiting (local) | **none** | empty |
| Waiting (spooled) | **kept** | empty |

**That asymmetry is load-bearing.** A local wait releases the source: there is nothing at the path, holding an unlinked inode open pins bytes nobody will read, and invariant #5 says observing a log must not disturb the writer. A **spooled** wait keeps it, because `SpooledLogSource` owns the `shared_ptr<SourceSpool>`, the spool owns the fetcher, and the fetcher is the thing retrying — releasing the source tears down the very machinery doing the waiting, and the log never comes back. `logPathIsSpooled()` is the existing discriminator and needed no change.

**`LogSource::originVanished()`** answers "is the thing I was opened from still there", non-pure and false by default — the third arrival by the route `wasReplaced()` took in M11 and `isComplete()` in M12. Two of those three now make the same point: the non-pure-virtual seam is the right shape for "only some sources can answer this". The implementations differ exactly as the interface predicts: a mapped source re-stats its path, a buffered one asks `QFileInfo::exists` (**not** `pathIdentity()` — originally because the Windows stub returned 0 for every file, and still, now that it is real, because 0 means *unknown*: a file that is gone, a file that will not open and a volume with no usable index all answer alike, and only the first is a log that is not there), and a spooled one reads its fetcher's state.

It is an **observation, not the guess invariant #5 forbids**. "The file is gone" is what a stat answers; "the file is finished" is not, which is why `isComplete()` needs loftail to have produced the bytes and this does not. It is also distinct from `wasReplaced()`, and the two are checked in that order: replaced means something *else* is at the origin and rescans, vanished means *nothing* is and waits.

**The grace period is what keeps a rotation silent.** `logrotate` renames and then creates, and a check landing in that gap sees a path with nothing at it — indistinguishable, in that instant, from a deletion. So vanishing must hold for 2 s before the view is cleared. It is measured as **elapsed time, not a count of checks**: the filesystem watcher fires checks too, and a rotation produces a burst of them at exactly the moment the path is empty, so counting them would shorten the grace period precisely when it is needed.

**Resuming needs the owner, because the pattern lives there.** A document that opened waiting has never sampled a byte, so its format and encoding are unsettled — `formatSettled()` means *settled against real bytes*, which is why a spooled source that opens empty does not count. Settling them needs an `IFormatProvider`, and invariant #3 keeps the pattern string out of core. `LiveController` therefore emits `resumeRequested()` and the window calls `Document::resume(provider)`. The cost is stated in the header: a document whose owner never connects that signal waits forever, by design rather than by accident.

**No dialog on arrival.** The log turns up on a watch tick, for a tab that may not be on screen, so raising Preferences there is the "behind the user's back" case `MainWindow::openFile()` already refuses for the archive member picker. The remembered pattern is applied; if it does not fit, the log reads as plain text and the status bar points at the dialog. Nothing is persisted in that case, so reopening still offers the dialog properly.

**Waitable vs fatal** is decided in `Document::prepare()` by two questions, and both are needed. `logSourceAvailable()` is the "is it there" half; `logPathIsWellFormed()` is the "does it name a log at all" half. Without the second, `ssh://` — which parses into no host and never will — would open a tab that waits forever for something that cannot exist. Refusals (a changed host key, a rejected password, an archive naming no member, a dependency not built in) stay refusals with no tab.

#### 6.5.1 The transport half

A remote log's absence cannot be answered from a path: there is none to stat, and asking the far end costs a round trip on every tick. So the fetcher answers, through `FetchStatus::State::Waiting` — "the input is not there; still trying", distinct from `Error`, which is trouble with a source that *exists*. Both retry on the same backoff; the difference is what the user is told.

- `SshFetcher::start()` used to split its failures: unreachable or no-such-file **succeeded** into `Waiting` and spawned the worker anyway, while a refusal returned false. Since M17 it makes no such judgement, because it no longer connects — it publishes `Connecting`, spawns the worker and returns. Every outcome is then published rather than returned, and the tab is already on screen to receive it: a refusal shows the transport's own words and offers Reconnect (`SPEC.md` §3) instead of vanishing. What still fails an open outright is only what can be decided with **no I/O** — an address naming no host, an archive naming no member, a dependency not built in, a cache directory that cannot be created.
- `tailLoop()` gained a reconnect step — before M13 nothing ever re-established a dropped session, so a link that blipped stayed broken until the log was reopened.
- **Retries are non-interactive, without exception.** An unattended retry gets the agent, the usual keys, or a cached password — the common case, entirely automatic. Since M17 a prompt *can* be carried out of the worker (§6.3.3), and being able to is not permission to: a modal dialog for a log opened hours ago, while the user is doing something else, is exactly what must not happen. The rule is now enforced by `m_wantsPrompter`, set by only two things — the document's own opening, and the user pressing Reconnect — and consumed by the attempt it was granted for.
- **File ▸ Reconnect finally works.** It had never been able to clear the commonest refusal there is. §6.5.1 has always said the action "runs on the GUI thread and does have a prompter", but all it did was `poke()`, and the retry that followed called `establish(nullptr)` unconditionally: a host needing a password was asked again with nobody to ask, reported `NeedsPerson`, and re-latched. `pokeNow()` now grants the prompter as well as clearing the latch.
- A retry out of `Waiting` does **not** announce `Connecting` on each attempt. It would flap the state several times a minute, and because `originVanished()` reads it, the document above would bounce out of waiting and straight back into it.
- A retry connects with a **shorter timeout** than the first attempt (5 s vs 20 s). That used to be about *closing* — `stop()` joined the fetcher thread from the GUI thread, so a connect in progress was how long closing a tab on a dead host froze the window. Nothing joins a fetcher now (§6.3.3), and the number survives on a better reason: a background retry has nothing to lose by giving up early, the next one is seconds away, and every second it spends is a second an unreachable host is not being left alone.

**An archive whose container is not there** is where this nearly went wrong. `ArchiveFetcher::start()` runs on the GUI thread and feeds libarchive through `awaitInput()`, which waits while the transport underneath is healthy — and a transport that is *retrying* is healthy, so `ssh://downhost/bundle.tar.gz/app.log` would have spun there forever. The opening of the member is therefore deferred to the worker when the container's source reports its origin vanished (`beginExpansion()` is called from `start()` or from the worker, never both). A *local* container never reaches the fetcher at all: `logSourceAvailable()` asks about the container, so `Document::prepare()` classifies it as waitable first.

### 6.6 Reloading by hand, and what stopWorkers() is for

`SPEC.md` §3 adds one deliberate gesture to a subsystem that is otherwise entirely automatic: **View ▸ Reload (F5)**. It exists because every other repair path is invisible by design — a rotation reloads silently, a wait resolves itself — so when what is on screen has stopped agreeing with the file there was nothing for the user to reach for.

**It re-reads with the format the document already has** (invariant #3). Re-resolving the settings tree was considered and left out: it makes F5 two features whose failure modes are hard to tell apart, and "re-read this file" is the one that was asked for.

**A format change is the same operation with one call different**, so it is the same function (`rebuildDocument`, `KeepFormat::Yes`/`No`). What they share is the half that is easy to get wrong — the worker teardown order, the model-reset bracket, re-arming the watch on *both* outcomes, and handing the scan to `IndexController` — and two functions promising to agree about that is how one of them quietly stops entering the waiting state when the log has gone.

**`applySettings()`'s pattern/encoding branch had done nothing since M9, and this is what fixed it.** It called `openWithSettings()`, whose second act is "reopening a file already open just raises its view" — and the file being reformatted is by definition already open, so the freshly prepared `Document` was discarded and the existing tab raised. Before tabs (`f197c0d`) that line read `teardownDocument()`, which is exactly what had made a format change reindex; M9 replaced it and nothing noticed, because no test drove a pattern change through a real window. Preferences ▸ *Apply to current file*, the timestamp header menu and `resumeWaitingDocument()`'s `FormatOutcome::Chosen` all rode on it. `tst_reload`'s three format cases fail against the old code and are what pin it.

**`Document::reformat()` is `reopen()` with a new format, and deliberately not `prepare()`.** `prepare()` is for a document that does not exist yet: it resets the run-start matcher, opens `Interactive` — so a remote path with no live spool would *connect, from a settings dialog* — and on an outright failure clears `m_path`, which is right for an open and wrong for a document sitting in a tab that must not be left pathless. `reformat()` is the `resume()`-shaped sibling: `Reuse` policy, the path kept, a log that has gone becoming a wait, and the run-*start* pattern left alone because a format change is not asking to change it.

**A format change rebinds the panes; a reload does not.** Which axes a pane offers is decided in `setDocument()` from `document->format()` — no `%t`, no Thread axis — and the `Document` pointer has not moved, so `activeDocumentChanged` does not fire on its own. The rebind goes through `stashPaneState()` / `hydratePanes()`, exactly as a tab switch does, because `AxisEditor::setDocument()` clears the pane's discovered-value bookkeeping by design and `restoreState()` is what puts the user's choices back. `KeepFormat::Yes` skips it: the format did not move, so there is nothing to re-ask.

**A format change made while the document is WAITING re-settles on arrival instead.** There are no bytes to re-read and its workers must not be torn down, so `applySettings()` calls `Document::unsettleFormat()` and returns. Without that call a log that vanished *after* being read is still `formatSettled`, and `resume()` would bring it back wearing the format it had when it disappeared.

**The seam already existed and was unused.** `DocumentContext::stopWorkers()` was written for exactly this — "stop the live watcher and the indexing worker without tearing the context down, so a rescan can rebuild them over the same `Document`" — and had no caller but the destructor. `Document::reopen()` is `rescan()` minus the scan, split out so the two callers differ about **who does the reading and about nothing else**: a rotation scans inline on a watch tick with nobody waiting, while a reload hands the scan to `IndexController` so a multi-gigabyte log shows a progress bar instead of freezing the window. Making them one function rather than two that promise to agree is the point; the failure mode of two is that one of them quietly stops entering the waiting state when the log has gone.

Four things about it are easy to undo:

- **`reopen()` leaves the index EMPTY.** `rescan()` replaces the whole thing in one assignment and would not care, but `IndexController::onBatch` **appends** into that same object — so a reload that skipped the clear would produce one copy of the log after another, growing by a whole file each time.
- **The live watch must be re-armed on the failure path too.** `stopWorkers()` destroyed it, and a log that vanished between the key press and the reopen is in the waiting state, where the watch is the only thing that can bring it back. `startWatching()` is split out of `onIndexFinished()` for that reason and is called on both paths.
- **The `Document` is reused, never replaced.** Everything per-file hangs off it (invariant #7) and every pane is bound to it by signal; swapping it would strand all of them. Only the `IndexController` is rebuilt — the model and the digest model are what the live views hold.
- **A WAITING document is poked, not reloaded.** There is nothing to re-read, and tearing its workers down would stop the one thing making progress. For a spooled document F5 therefore means `spool->poke()`; for a local one the 750 ms tick is already retrying and F5 correctly does nothing.

### 6.7 loftail's own log

`SPEC.md` §3 "Diagnostics". `DiagnosticLog.h` — always compiled, always on, thread-safe with a `std::mutex` (§13.1 bans `QMutex` in core), capped at 1 MB with exactly one rollover so the total on disk is bounded by twice that.

**On by default is the whole design.** A diagnostic log that has to be enabled before it is useful is never on when it is needed; the cost of that decision is bounded by the cap and by what is written, not by a setting.

**What is written is attempts and outcomes, and states that changed.** Never a tick that changed nothing — which is a real constraint rather than a style note, since the two call sites are a 750 ms watch tick and a fetcher poll. `SshFetcher`'s three status setters compare before logging, so `setState(Live)` on every poll that fetched something produces one line for the *transition* and none afterwards. Where an attempt genuinely does repeat — a host down for an hour, retried every five seconds; a waiting document polled every 750 ms — `diagLogEvery()` collapses it to one line a minute and **counts** the suppressed ones, because a log that under-reported how often loftail tried would be lying about the one thing it is read to answer.

**It is not translated**, and that is the same call `SshExecCommands`' shell text and the log4cplus conversion patterns get (§9.1). The audience for a line in it is whoever is diagnosing the fault — often not the person at the keyboard, and often reading it pasted into an issue — so the tokens have to mean one thing in every build and every locale. `fetchStateName()`, `sizeSourceName()` and `SshSession::modeName()` exist for that: they are the greppable spellings, deliberately not routed through any status-bar wording. Counts are written `records=N` rather than as prose, so there is no plural to get wrong.

**It never records a credential.** That a password was asked for and whether the server accepted it is the diagnostic question; the password is not part of it. Host-key fingerprints *are* written — they are public by definition, they are what the user is asked to compare, and they are exactly what somebody checking a refusal by hand needs.

**The state object is a leaked-on-purpose singleton.** A retired fetcher outlives the window (§6.3.3), so a `static QFile` destroyed at exit would be a use-after-free on precisely the thread most likely to still be writing.

## 7. Model, view, and filtering

### 7.1 Variable row heights — why not `QTableView`

`SPEC.md` §5 requires multi-line records to render at full height in the table. That single requirement rules out `QTableView`, and it is worth being explicit about why, because the reason is not obvious and the workaround is not viable.

`QTableView` delegates vertical geometry to `QHeaderView`. Uniform row heights give O(1) scroll math. Non-uniform heights require either `resizeRowsToContents()` — which calls the delegate's `sizeHint()` for **every row in the model**, an O(n) pass that is unusable at millions of records — or per-section sizes stored in `QHeaderView`, which materializes a per-row entry and defeats the entire lazy-index design from §5. There is no lazy per-row height API. Retrofitting this later would mean replacing the view, the scroll model, and the selection plumbing at once.

**Therefore: a custom `LogView : QAbstractScrollArea`**, painting visible rows directly.

The design that makes this cheap:

- **Scroll in line units, not pixels or records.** The vertical scrollbar's range is the total physical line count. Every line is the same height (fixed-pitch font), so line units map to pixels by a single multiply.
- **Two-level prefix sums over `Record::lineCount`.** Store a cumulative line count every 4096 records; resolving a scroll position to a record is a binary search over the block array plus a short linear scan within one block. That is O(log n) with a cache-friendly inner loop, and appending during live tail only touches the last block.
- **Overhead:** one `quint64` per 4096 records — negligible next to the 24-byte index itself.
- Painting walks forward from the first visible record until the viewport is full. Only visible records are ever touched, preserving the §5 laziness guarantee.

Reused rather than rebuilt: `QItemSelectionModel` for selection state, the `LogFormat` field map for columns, and a `QStyledItemDelegate`-style paint helper per cell. Hand-rolled: hit-testing, rubber-band and shift-click range selection, keyboard navigation, and clipboard serialization.

**Eliding and the tooltip are one question asked twice, of the same width.** `SPEC.md` §5 asks that a value too wide for its column say so and be readable in full on hover. The painting half is `QFontMetrics::elidedText(…, Qt::ElideRight, sectionSize)` for every fixed-height cell — and, with wrap off, for each physical line of a message on its own, since each is clipped on its own (invariant #2). The tooltip half is `LogView::viewportEvent()` answering `QEvent::ToolTip`, and it asks the *same* function of the *same* section width, so a tooltip appears exactly where an ellipsis was painted and nowhere else. It is not served through the model's `Qt::ToolTipRole`: whether a value fits is a question about the column's current width, which nothing below the view can see, and a role-based answer would show for every cell whether or not anything was cut off. Nothing is precomputed and nothing is held — the text is decoded through `LogModel` when the hover arrives, as painting decodes it when the paint arrives (invariant #1).

The **header** is a `QHeaderView` and needs both halves separately: its `textElideMode` defaults to `Qt::ElideNone`, so it is set to `ElideRight` (Qt's styles honour it through `QStyleOptionHeaderV2`), and its tooltips arrive on *its* viewport rather than the view's, so `LogView` filters that viewport. The width the header is measured against is the style's `SE_HeaderLabel` rect and not the raw section, because a section spends a few pixels either side on its margin — that margin is the difference between a caption that fits and the one painted as "Priorit".

**Column widths are two questions, and only one of them may walk the file.** `SPEC.md` §5 asks that a column open at a width that fits and that the user be able to fit or reset it by hand.

- A **seed** is what a column is worth before anyone has looked at it: `max(header caption, per-role character allowance)` measured through the view's own `QFontMetrics`, plus a gutter, clamped to `[40, 2400]` px. In **characters**, never in pixels — every column renders in `monospaceFont()`, so a character count is the one unit that survives a font size nobody chose, and a pixel constant is a guess about a font that has not been resolved yet. `charWidth()` and `textWidth()` fall back to 8 px per character when the metrics answer 0, which is what a platform with an **empty font database** answers (Windows offscreen ships no fonts) — unfloored, every column there would collapse to its minimum.
- The seed runs **exactly twice per view**: in the constructor, where the index is empty and the caption is all there is, and again from `MainWindow::onIndexFinished`, where the intern tables are complete and the Subsystem/Thread columns can take the widest name in the file — one walk of a list the filter pane already shows and not a single record decoded (invariant #4). Never per ingest tick and never on the paint path. The scan-completion seed clamps a name to 40 characters, because a seed is not a fit.
- A **fit** (`fitColumnToContents`, the header menu's *Fit to Contents*, and `QHeaderView::sectionHandleDoubleClicked` — which Qt emits and leaves to whoever drives the header, so with no item view behind it nothing used to happen) measures the widest value there actually is. It is **bounded**: the metadata columns read the intern table (at most 20,000 names), Priority reads the six level words, and everything else samples **at most 400 records** — the visible ones first, since a fit that leaves the row under the cursor elided reads as broken, then an even stride across the whole view. A multi-line message is measured line by line (invariant #2), and the result is clamped like a seed.
- **The seed never touches a column anybody has spoken for.** `m_userSizedColumns` is set by the user's own `sectionResized` (excluding the 0 that a hide/unhide reports), by a fit, and wholesale by `restoreColumnState()` — session restore creates the views and restores their layouts *before* indexing starts, so without that last one the scan-completion seed would silently widen a column narrowed in the previous session. `resetColumnWidths()` clears the lot and seeds again, which is the only way back. `applyColumnWidth()` sets `m_applyingColumnWidths` so this class's own resizes are not read back as the user's.

Displayed height is capped at 100 lines per record (`SPEC.md` §5). `lineCount` is clamped for display only — the prefix sums use the clamped value so geometry stays consistent, while copy operations use the true byte range.

### 7.1.1 Line wrapping and the two geometry modes

`SPEC.md` §5 makes wrapping a three-mode setting, and *always on* is the mode that breaks the scheme above: a wrapped record's height depends on the viewport width, so every resize invalidates every height. Measuring all records on resize is an O(n) text-shaping pass — worse than the `QTableView` problem this design exists to avoid.

Hence two geometry modes behind one interface:

**Exact mode** (wrap off, or selected-record-only). Height is a property of the record alone. Prefix sums are exact, the scrollbar is exact, and the *selected-record* case is a bounded special case: one record's height changes, so patch that single block's sum rather than rebuilding.

**Estimated mode** (wrap always on):

- Exploit the fixed-pitch font — wrapped height needs **no text shaping**, only a character count: `ceil(charsInLine / viewportCols)`. That reduces the problem from measuring text to counting characters. The font is not incidental to styling: `monospaceFont()` (`src/ui/Fonts.h`) takes the family the platform designates as fixed-width and applies it to the whole view, header included, so every column shares one uniform advance. Anything that gives a column a proportional font invalidates this estimate.
- Measure exactly the blocks that have been visited; estimate the rest from a running average of characters-per-record observed so far.
- The scrollbar is therefore approximate and **refines as the user scrolls**, which `SPEC.md` §5 states plainly rather than hiding. Scroll position and navigation stay exact; only the thumb geometry is estimated.
- Cache measured block heights keyed by viewport column count; a resize invalidates the cache, and recomputation is debounced so a drag-resize measures once at the end rather than per frame.

The estimation machinery is only reachable in *always on* mode — the other two modes never construct it. This keeps the common path exact and simple, and confines the complexity to the mode that demands it.

**This is the highest-risk component in the project, and 7.1.1 is the highest-risk part of it.** Prototype exact mode first in M2a to validate the core scheme; estimated mode can follow in M2b once the foundation is proven.

### 7.1.2 Holding the view's place across a filter change

`SPEC.md` §6 asks that changing a filter not move the reader. Neither coordinate the view holds survives a re-apply on its own: the scroll value is a line index in the view's *own* line space, which the compact `FilteredIndex` remaps wholesale, and `m_current` is a view row, which `handleModelReset()` clears because for every *other* reset it would be a wrong row. **A source record ordinal is the one coordinate a refilter does not move**, so the anchor is expressed in those and nothing else.

- **A caller-owned bracket, not a hook inside the reset.** `LogView::beginFilterUpdate()` / `endFilterUpdate()` sit either side of `LogModel::beginFilterReset()` / `endFilterReset()` in `MainWindow::applyFiltersFor()`. Outside, because `QItemSelectionModel` clears itself from the same `modelReset` signal — it is connected before `handleModelReset` — so a restore running inside the reset would be undone by it. And *only* around a filter re-apply: a rotation rescan, a resume from waiting, a digest republish and `setViewIndex()` all replace the record space itself, where a source ordinal means something different or nothing. `applyFiltersFor()` takes a `KeepPosition` for the two callers that position every view explicitly on the next line (opening at the file's end, and picking a run), which would otherwise scroll twice.
- **`FilteredIndex::viewRowOf()` / `viewRowAtOrAfter()`** are `sourceRow()`'s inverse and its nearest-survivor form, mirrored onto the `LogModel` seam (§7.5) so a view asks its model rather than the document. `viewRowAtOrAfter()` is a binary search and therefore **means nothing over a subset published out of order** — which the digest is, since `publishDigest()` reorders its ordinals by timestamp. So `FilteredIndex` tracks `m_ascending` and `viewRowOf()` falls back to a scan; `popLastVisible()` deliberately leaves the flag alone, because dropping the tail can only preserve ascendingness and staying conservatively false costs a scan, never a wrong answer.
- **Selection, then geometry, then the target line, then the scroll.** In `WrapMode::SelectedRecordOnly` the selection *is* part of the line space (`selRecordForGeometry()` feeds the geometry statics), so a target computed before the selection is restored is computed against a different mapping than the one it is applied to — the anchor row lands short by the selected record's extra wrapped lines. This is why the restore uses a non-scrolling `selectRecordSilently()` rather than `setCurrentRecord()`, which scrolls.
- **The follow guard is a flag, not a `QSignalBlocker`.** `endResetModel()` narrows the scroll range and Qt clamps the stale value into it; that arrives at `updateFollowFromScrollPosition()` as an ordinary scroll, and a clamp landing at the bottom is how a *detached* view used to start following again in silence. Blocking the scrollbar's signals instead would suppress `rangeChanged`, whose connection to `QAbstractScrollArea`'s `_q_showOrHideScrollBars()` is **queued** — so the scrollbar's visibility would stop tracking a range that a filter change is precisely what moves. `endFilterUpdate()` carries the follow state over verbatim rather than re-deriving it, and a following view is sent to the end instead of anchored.
- **A hidden selection is kept as a source ordinal (`m_stickySource`) and never moved to a neighbour.** Its invalidation is one line in `handleModelReset()` guarded on *not* being inside the bracket, which is exactly "any reset that is not a filter re-apply forgets it" with no per-caller bookkeeping; `setCurrentRecord()` clears it too, since an explicit pick is the user moving on.
- In AlwaysOn the **record** is exact and the **line** is the estimator's best answer, as it already is across a resize (`applyDebouncedResize()`). `handleModelReset()`'s `m_estimated.clear()` must stay: `geom()` hands back `FilteredIndex::m_compact`, whose *address is stable* across `setVisible()`, so `ensureEstimatorBound()`'s identity test would fail to rebind whenever a refilter happened to leave the block count unchanged.

### 7.2 Model and filtering

- `LogModel : QAbstractTableModel` — rows are records, columns come from `LogFormat::fields`. `data()` parses lazily; it is on the paint path and must not allocate more than necessary. Prefer `QStringView` into the mapped bytes. The model stays a `QAbstractTableModel` even though the view is custom: it keeps the proxy-filter machinery and the model/view separation intact.
- Filtering via a `QSortFilterProxyModel` subclass over `LogModel`. Predicates read `Record::priority` and `Record::loggerId` directly, not display strings.
- Priority filtering is a single `>=` test against a minimum level (`SPEC.md` §6). This requires the `Priority` enum to be **declared in severity order** (`Trace < Debug < Info < Warn < Error < Fatal`) so the integer comparison is the severity comparison. `Unknown` (unparsed records) sorts below `Trace` so a minimum level never hides unparsed lines — they carry no priority to filter on and must stay visible.
- Subsystem and thread filtering are `QSet<quint32>` of interned ids. Interned id **0 is the "field absent" sentinel** and is exempt from its own axis, for the same reason `Unknown` is exempt from the priority minimum: a record that never carried the field cannot be judged by a filter on it.
- **An axis that excludes nothing is written as inactive.** The subsystem axis ships enabled (`SPEC.md` §6) so its list is live on the first click, but "enabled with every subsystem ticked" narrows nothing. `FilterPane` collapses that state to `enabled = false` in the `FilterSet`, keeping `FilteredIndex` on its identity path instead of materializing a compact copy of every record for a filter that hides none of them. The checkbox stays ticked; only the model-side flag is dropped. The collapse is exact, not heuristic. The priority axis has the same collapse against `kPriorityByIndex[0]` (TRACE) and it is now **only reachable from stored data**: the axis ships disabled and the combo no longer offers TRACE, so nothing the user can do produces an enabled-at-TRACE state.
- **TRACE is dropped from the priority COMBO, never from `kPriorityByIndex`.** That array is the on-disk format: `MatchCriteria::toJson()` writes `minPriorityIndex` as an index into it and `fromJson()` reads it straight back, so removing its first row would reinterpret every stored preset and session one level too severe — a saved INFO floor loading as WARN — and no version bump could catch it, since `PresetStore` gates on exact equality and discards on any change (§8, "Growing the highlight axis set did not bump either schema version"). So the table keeps all six levels and `AxisEditor` skips TRACE when populating, carrying each row's `Priority` in its item data. **The combo's row order is therefore not `PriorityChoice`'s index order**, and `comboPriority()` / `setComboPriority()` are the only two places that relate them; nothing may index the combo by a `PriorityChoice` index. A TRACE floor arriving from stored data is not promoted to DEBUG — that would convert a filter which showed everything into one hiding every TRACE record — but taken for what it always meant, "do not narrow by level", and applied by leaving the axis unticked. The view is identical before and after, which is the test of a migration that costs nothing.
- **Newly discovered values arrive selected.** The subsystem/thread lists are repopulated repeatedly as the scan turns up names, so `FilterPane` tracks every name it has ever listed: a name absent from that set is new and starts checked, while one the user unticked stays unticked. Without it, an enabled-by-default axis would start dropping records mid-scan. The set is per-binding and is cleared in `setDocument()` — carried across a rebind it would leave the next file wholly filtered out.
- **...unless the selection is a restriction, which is a different thing that looks identical.** `MatchCriteria::loggerRestrictive` / `threadRestrictive` mark a selection made by *pointing at one value* (`AxisEditor::showOnlyValue()`, the record menu's edit — §7.4) rather than by ticking a list. The name list alone cannot tell the two apart, and the discovery rule above is exactly wrong for the second: "show only `net.http`" would silently acquire every subsystem the scan found afterwards, and on a tailing log it would keep acquiring them for as long as the file is open. Restrictive turns the discovery rule off for that axis without turning it into an exact load — a name the user *types* still arrives checked, because typing it is the request to see it. It is **persisted**, unlike `coversAll`, because it is part of what the selection means and a restored session or applied preset must not widen where the original did not. It is written to JSON only when true, so every state that predates it serializes byte-identically and neither store's schema version moves.
- **...and the flag is a control, not a bool, which changes who is allowed to clear it.** `AxisEditor` has no `m_loggerRestrictive`: the axis's **"Others" row is the state** (`restrictiveFor()` reads it, `setRestrictiveFor()` writes it), so the control and the criterion cannot fall out of step and there is nothing to keep in sync. The rule used to be invisible, reachable only through `showOnlyValue()`, and was cleared by *any* hand edit to the list — one tick, All/None/Invert, a manual add — on the reasoning that the user was taking the axis back. With the rule on screen that is wrong twice over: a control that unticks itself when the user ticks something else is worse than no control, and `setAllChecked()` emits `itemChanged` per item, so `None` would clear the very restriction it means to set. So a list tick now says nothing about the rule; **All/None/Invert set it explicitly** (and after the list edit, not before), and `showOnlyValue()` still sets it. Two consequences to keep: every programmatic write must sit inside `m_populating` — `setDocument()`'s reset emits `itemChanged()`, and unguarded it would reach `changed()` and have `HighlighterPane` write the incoming document's defaults into whichever rule is selected — and the control ships **checked**, which is what `populateList()`'s discovery rule already assumed.
- **The control is the list's first ROW, which is what keeps it one kind of answer.** It was a "New" checkbox in the All/None/Invert column, and that column is commands while the rule is a tick — read as a fourth button, and in the Highlighters pane it sat a few pixels from that pane's own *New* button, which makes a rule rather than answering one. As row 0 of the list, ticked or unticked like every name below it, "these subsystems, and the others" is one list of ticks and one question. Five things fall out of it and each is silent if undone: the row is marked by `kOthersRole` and skipped from `kFirstValueRow`, because `checkedNames()` would otherwise put the *translated* label into `MatchCriteria::loggerNames`, into every preset and into the session file; `QListWidget::clear()` must never be called on a value list (`clearValueRows()` keeps row 0), because the row **is** the state and `populateList()` is handed that state rather than re-deriving it; `setAllChecked()`/`invertChecked()` skip it and All/None/Invert set it **explicitly**, since `invertChecked()` is followed by a read-and-flip of the rule and a sweep would flip it twice; `narrowList()` skips it, because it is not one of the names being searched and hiding it takes the rule off screen exactly while a selection is being built; and `allChecked()` skips it, because `loggerCoversAll` asks whether the selection covers what the user was *offered* — an unticked "Others" over a fully ticked list excludes nothing yet, and stops being all-checked by itself the moment a value arrives unticked.
- **Ctrl+click is `showOnlyValue()` reached from the list, and it is an EVENT FILTER on the viewport rather than a connection, because the press has to be *taken*.** Left to the view, that same press either toggles the tick under the cursor (on the indicator) or moves the selection (anywhere else), and either would land on top of the exclusive edit rather than instead of it — `itemChanged` would then arrive after `checkOnly()` had finished and untick the one row it had just ticked. So `AxisEditor::eventFilter()` claims `MouseButtonPress`/`MouseButtonDblClick` with **exactly** `Qt::ControlModifier` (not "contains Control", which would swallow chords the view is entitled to) and returns true, but only when the point actually hits a row — a Ctrl+click on empty list space is left alone. It is on `QListWidget::viewport()`, not on the list: a view's mouse events arrive at the viewport, and a filter on the list itself sees nothing but the scroll bars. `checkOnly(axis, item)` is the shared body, and `showOnlyValue()` is now a lookup by name in front of it, so the menu edit (§7.4) and the chord cannot drift; the row-versus-name distinction matters only in that `showOnlyValue()` must look the item up **after** `ensureListed()`, which may have rebuilt the list under it. The "Others" row is a legitimate target — `setRestrictiveFor(axis, !isOthersRow(target))` is the whole difference — so "only what the scan has not found yet" falls out of the same body rather than being special-cased away.
- Time-range filtering is two `qint64` comparisons against `Record::timestamp`.
- **The time editors are seeded from the index, and the seed keeps running.** They cannot hold "no bound" — `QDateTimeEdit` always shows *something*, and its default is the year 2000 — so an unseeded bound is not neutral, it is a filter that hides everything. Seeding only in `AxisEditor::setDocument()` was therefore a bug rather than a nicety: that runs from `activeDocumentChanged` at open time, before the scan has produced one record, so `observedSpan()` failed and ticking the axis on a freshly opened log emptied the view. `refreshObservedSpan()` runs from `refreshDiscoveredLists()` (i.e. as the index grows) and from the group's own `toggled(true)`, and is suppressed by `m_timeUserEdited` — the same hand-edit-versus-repopulation distinction `loggerRestrictive` draws one bullet up. Three things it is easy to undo: the flag must be set **before** `setChecked(true)` in `setTimeBound()`/`setTimeRange()`, because ticking the group re-enters the seed synchronously and would overwrite the bound just set; `refreshObservedSpan()` must bail while `m_populating`, for the same reason from the other side; and it must **re-read `m_renderZone` from the document** before rendering, because a document bound before it was opened has a default-constructed — i.e. **invalid** — `QTimeZone`, `fromMSecsSinceEpoch()` through one yields an invalid `QDateTime`, and `QDateTimeEdit::setDateTime()` ignores that and silently stays at the year 2000. That is the waiting-document path (`SPEC.md` §3), so it is the normal case for a remote log, not a corner.
- **Message-text filtering is the one axis with no fast path.** It cannot use interned ids; it must decode and scan message bytes per record. Order the predicate chain so the cheap integer tests run first and text matching only sees what survives them — on a typical filter set that is a small fraction of records. For substring matching use a `QByteArray` search over the encoded form rather than constructing a `QString` per record; only regex matching needs decoded text.
- Find/Find Next (`SPEC.md` §5) shares the text-matching code with message filtering but not the mechanism: find walks the proxy's visible rows from the cursor and returns a row index, changing no filter state.
- Highlighting is **not** a proxy: it is applied in `data()` via `BackgroundRole`/`ForegroundRole`, evaluating the ordered rule list and returning on first match (`SPEC.md` §7). The matched rule carries an independent background and foreground choice, each either a palette index or *default*; a *default* returns an invalid `QVariant` for that role so the view falls back to the normal theme color. First-match-wins is per-rule, not per-role — a rule that sets only the background does not let a lower rule supply the foreground. **Since M19 a matched rule supplies a SET of actions and colour is one of them, so first-match-wins is also per ACTION**: the rule list is asked "which rule colours this record", and a rule that does not colour is not a candidate for that question at all (§7.5).
- **Highlight rules match on the same five axes as filters, through the same predicate.** A `HighlightRule` embeds a `MatchCriteria` — the *portable* form of the axes (subsystem/thread names, a priority level, display-zone wall clock, a pattern string) as against `FilterSet`'s *resolved* form (interned ids, UTC ms, a compiled regex). `HighlighterSet::resolve()` turns each rule's criteria into one `FilterSet`, so there is exactly one predicate chain in the codebase and the two features cannot drift into half-overlapping axis sets. Two arguments to that resolve carry the whole difference:
  - `AbsentField::DoesNotMatch` vs `::Matches`. A record lacking the field an axis tests must not be *hidden* by a filter (`SPEC.md` §4) and must not be *colored* by a highlight rule (`SPEC.md` §7). Same axis, opposite exemption, one flag on `FilterSet` rather than a second copy of the chain.
  - `NoOpAxes::Keep` vs `::Collapse`. Filtering collapses an axis that excludes nothing so `FilteredIndex` keeps its identity path; highlighting has no compact index to protect, and "≥TRACE" is a legitimate *color everything parsed* rule.
- **The two panes share the axis WIDGET as well as the predicate, and diverge in exactly ONE constructor-time answer** — `AxisEditor::Defaults`, which says which axes ship enabled (`SPEC.md` §6 vs §7). Everything else about how an axis looks and behaves is the widget's, unconditionally. `setHidesUnsupportedAxes()` was the second divergence and is **gone**: an axis this log's format cannot fill is left out in **both** panes. The Filters pane used to keep it, greyed, with the reason in its title, on the argument that it describes the whole log and so a missing axis is worth *saying* — but a section that can only ever say "not available here" is read once and holds its space for the session, in the pane with five axes competing for the height of one dock. Being *switched off* is a state the user can undo and its controls are therefore worth reading; a field the format does not carry is not. The disabling is a separate step and still happens in `setDocument()`, applied whether or not the axis is on screen — so a restored session or applied preset that arrives with such an axis ticked has it dropped by `resolve()` and cannot edit it back into force from a pane that no longer shows it. A further divergence, `setCollapsible()`, is **gone** for a related reason: the Highlighters pane collapsed each axis to its title row until it was ticked, and that was the wrong trade there for the same reason the Filters pane had already reversed it — an axis whose controls appear only once it is switched on can be explored but not read. The scroll area absorbs the height. There was briefly one more, `setFlatAxes()`, and it is **gone** the same way. An axis is a title row over a hairline rather than a framed panel, now in **both** panes and unconditionally: it entered as the Highlighters pane's answer, because its axes then sat inside a framed `Condition` box (gone since the actions moved into the rule table) and a framed axis in there put three borders between the pane and the subsystem list, but the Filters pane wanted it for the same reason one level up — an axis is a section of a pane, a pane is a frame already, and five framed panels stacked in one dock draw five borders around things nothing else groups. Since no caller passes false, the flag is not a decision, and `tst_filterpane::theAxesAreLinesNotFrames` is what notices if a frame comes back on one side only.
- **The hairline runs along the title row, which is why it is PAINTED and not a `QFrame`.** A group box's title row is drawn by the style and is not a layout — there is no cell beside the title to put a line in, and a `QFrame` added to the box's layout lands *under* the title rather than alongside it. So `SectionBox` (`src/ui/SectionBox.h`) is a `QGroupBox` that draws the line itself in `paintEvent`, from `QStyle::subControlRect(CC_GroupBox, …, SC_GroupBoxLabel)`'s right edge out to its own — asked of the style rather than measured with `fontMetrics()`, because the label rect already accounts for the check indicator, the style's spacing and the alignment, and a hand-rolled sum is wrong by a different amount per style. Subclassing rather than rebuilding the header out of a checkbox and a frame is what keeps everything else: the title row is still the enable control, `isChecked()`/`setChecked()`/`toggled()` are still where every caller expects them (the five axes remain `QGroupBox *`), and Qt still greys the body — the hand-written `setEnabled()` standing in for that is the exact special case the priority axis was rewritten to remove.
- **A section's title row is dragged LEFT with a style sheet, because that is the only lever there is.** Breeze — the style on the reference KDE desktop — **centres** a group box title and **ignores `QGroupBox::alignment()`** doing it: the label rect is identical with and without `setAlignment(Qt::AlignLeft)`, measured at x=152 of a 380 px box. Since a checkable box's title row *is* the axis's enable control, that put all five enable controls in the middle of the pane while every control they govern starts at the left edge, and it left the hairline above running from mid-pane out, since the line starts where the style says the label ended. `SectionBox`'s constructor therefore sets a `QGroupBox::title { subcontrol-position: top left }` rule, which overrides it; checked on renders under Breeze and Fusion, it keeps the frame of a framed box, keeps the check indicator's own look, and does not reach the body — no rule matches a child, so children go on drawing through the desktop's style. It applies in **both** panes, because the axes are one widget and an enable control's position is not something the two are allowed to disagree about. `tst_filterpane::theAxisEnableControlsSitAtTheLeftEdge` asks the style for the indicator rect and also asserts the rule is present, because under a style that left-aligns anyway — every style the suite is likely to run on — the geometry check cannot notice the rule's removal. **The same rule settles the opposite case**, which is what makes it one decision rather than two: `setHeading()` centres the title and bolds it, for a box whose title row is a *caption* over other controls (`Condition`, `Action`) rather than a control itself. Bold comes from the style sheet and **not** from `setFont()`, because a widget's font is inherited by its children and bolding the box would bold every label, list and combo inside it. Hard left is right for a control and wrong for a caption — a centred heading dragged into the corner reads as a control that has lost its checkbox — and on Breeze the distinction had simply been invisible, since everything was centred. A heading also carries **top** padding, which is not decoration: once a style sheet places the title, the frame starts at the widget's own top edge and the title is laid *inside* it (measured: frame top 0, label y=0), so with no padding the caption's ascent begins on the border line. Top padding is the half that moves the words — bottom padding moves the body and leaves them where they were — and a taller `margin-top` on the box, the thing a style sheet suggests instead, drags the title down onto the line and squeezes the body. Checked on renders under both styles.
- **`Plain`, not the idiomatic `Sunken`, and retinted.** Fusion draws a sunken `HLine` in Light/Mid, and on the stock light palette that is not visible against the pane at all — measured on a render, not assumed. Full `WindowText` is far too heavy for a seam, so the pen is `UiColors::dividerColor()`: most of the way from the text colour toward the surface, derived rather than read out of `QPalette::Mid` for the same reason Sunken fails. Resolved **per paint**, which buys two things a palette written once at construction does not: the line follows a theme switched mid-session, and it takes `QPalette::Disabled` when the section is switched off, so it dims with the title beside it instead of staying at full strength over a greyed body. That colour group is a parameter of `dividerColor()` precisely so the disabled case cannot be forgotten.
- **The text axis reaches the paint path, so its cost is bounded twice over.** `HighlighterSet::match()` takes the decode as a *callable* (the same lazy-`MessageFn` shape as `FilterSet::accepts`) and invokes it only once a rule's integer axes have passed and that rule has an active text axis, memoizing the result across the rule list — N text rules cost at most one decode. The decode is `Document::messageText()` (capture-free `recordStartRe`, whole-line fallback), not `cellText()`'s full-capture `recordRe`. And `LogModel::rowColors()` resolves both roles in one first-match-wins pass, because `LogView` would otherwise ask for `BackgroundRole` and `ForegroundRole` separately and run the list — and the decode — twice per record. The bound is one decode per *visible* record per repaint: tens of records, against the ~270 ms a text *filter* costs over 1M (`PLAN.md` M4). No cache is warranted; one would need invalidating on filter reset, live append, rule edit and theme change.
- **`resolve()` is where everything expensive happens**, and it runs per rule edit, per rescan and per display-zone change — never per record. It is also load-bearing: an unresolved `HighlighterSet` matches nothing, so every path that installs rules (session restore included) must call `Document::resolveHighlighters()`.
- Sorting is deliberately not offered: records are inherently in chronological order, and sorting a lazy offset index would require a full materialization pass.
- **Filtering invalidates the §7.1 prefix sums**, since hidden records contribute no height. Rebuild the block sums over the visible subset whenever the filter changes — a single linear pass over the index with no parsing, comfortably inside the §11 repaint budget. Do not attempt incremental patching; the full rebuild is fast and much harder to get wrong.

#### 7.2.1 Filter context (`grep -B`/`-A`)

Context (`SPEC.md` §6) shows N records either side of each message-text match, dimmed. It is the one thing the filter chain cannot express, because it is not a property of a record: whether row *r* is shown depends on rows *r±N*. So it is not an axis and not a `FilterSet` field — it is two ints on the `Document`, beside the filters, and one **forward pass** (`ContextEmitter.h`) that turns "which records match" into "which records are visible, and which of those are only neighbours".

- **The pass takes the view predicate cut along the text axis**, not along the run bound. `inBound()` is the *stream being searched* — the run bound plus every non-text axis, `Document::inContextStream()`, integer comparisons only — and `matches()` is the *search*, the message axis alone, `Document::matchesTextAxis()`. Their conjunction is exactly `acceptsInView()`, so context at 0 changes nothing; `tst_filtercontext::theTwoHalvesOfTheViewPredicateComposeBack` pins that. Two consequences fall out of the cut rather than out of code: a neighbour always satisfies the other filters, and an **inactive text axis makes context inert** — `acceptsText()` returns true for everything, every in-bound row is a match, and no row is left to be context to. There is no gate to keep in step with the UI, which is why the Filters pane can put the spinners inside the message-text group (`AxisEditor::addTextExtra()`) and let a checkable group box grey them out.

- **Everything below it is unchanged**, which is why the feature is small: `FilteredIndex::setVisible()` already took any ascending list of source ordinals and rebuilt its own prefix sums, so a context record is just one more ordinal, and every piece of tested geometry — the exact line↔record statics and the `EstimatedGeometry` estimator alike — runs over it without knowing. The only new state is one byte per visible row saying "context, not match", which `LogModel::rowIsContext()` exposes and `LogView` renders as a dimmed row. Core has no palette, so core does not decide what dimmed *looks* like.
- **Context composes with the run bound rather than ignoring it**: the run bound is the cheapest term of `inContextStream()`, so pulling the lead-up in from the previous run cannot happen (`SPEC.md` §3a).
- **Context never activates the view on its own.** `applyFilters()` keeps its early-out: with no filter and no run there is nothing to be context to, and the identity path must stay allocation-free (§7.2 above).
- **“Either side” counts in-bound records, not ordinals.** `inBound()` now carries the metadata axes, so its holes are interior and arbitrarily wide: a `-B 2` under a WARN floor means the two nearest WARN-or-worse records, however many INFOs sit between. The leading window is therefore found by **walking back from the match over in-bound rows** rather than by computing `r − before`, and the trailing window by a **counter of in-bound rows since the match** (`ContextState::sinceMatch`) rather than by `r − lastMatch`.
- **The suffix invariant — the load-bearing claim.** Write *W(m)* for the oldest ordinal in the leading window of a match at *m*. After any emission step, the emitted set contains every in-bound row in `[W(lastMatch), lastEmitted]`. A new match at `r > lastEmitted` therefore needs only rows *above* `lastEmitted`: since `r ≥ lastMatch` gives `W(r) ≥ W(lastMatch)`, the rest of its leading window is already there. So **leading context is a tail append**, never a mid-list insert, and the live path extends the visible subset in place exactly as it did before context existed (§6, invariant #9). This used to rest on `inBound()` accepting a *contiguous* range of ordinals, because the window was ordinal arithmetic; the backward walk removed that dependency, and with it the constraint the run bound (§7.3) was carrying on its behalf. The walk stops at `lastEmitted` — which is what the invariant buys — so successive matches walk disjoint stretches and the whole scan stays O(n).
- **The live edge case is the provisional trailing record**, the one whose bytes can still change. Without context, at most its own view row can be wrong, so the tail is popped one row and re-evaluated. With `-B`, a provisional that *was* a match also dragged up to `before` neighbours in with it, so the pop widens to the start of its window — `Document::contextWindowStart(base, before)`, which counts in-stream records backwards, **not** `base − before`, which under any metadata filter stops short of the window and strands the orphans (`tst_filtercontext::liveFlipReachesBackOverRejectedRecords`). The re-scan must restart at **the same row it popped back to**, not at the provisional. Restarting at the provisional would drop any match inside the popped window from the view permanently and silently (`tst_filtercontext::liveProvisionalFlipDoesNotDropAnEarlierMatch`). The pop widens only when the provisional's class actually **flips**: if it was and still is a match, the invariant leaves the emitter at `lastEmitted == base − 1` and the re-emit reproduces it exactly, so paying `before + 1` row removals per tick would be pure churn — visible to a detached reader as the view jumping on every append.
- **No emission state is cached.** `ContextState`'s three fields are read back off the `FilteredIndex` at the start of each tick — `sinceMatch` as the count of visible rows above `lastMatch`, which are exactly that match's trailing-context rows —, which is why `rescan()`, `enterWaiting()` and rotation need no bookkeeping for context at all: they clear the subset, and the state clears with it.
- The whole `-B`/`-A` rule is a template over three callables, so it is testable as a string-in/string-out function and the one-shot and incremental callers cannot drift — the same move `acceptsInView()` made for the run bound.

**Threading:** indexing runs on a worker thread and reports progress incrementally so the view populates during the scan rather than after it. The model is updated on the GUI thread in batches (via queued signals) — batching matters, since per-record signals on a fast scan will drown the event loop. Indexing must be cancellable.

### 7.3 Run selection

A log file often concatenates several application runs (`SPEC.md` §3, Runs). Rather than a second view layer, a selected run is modelled as **one more bound composed into the existing filtered view**:

- A run is a contiguous record range expressed as a half-open **byte-offset interval `[startOffset, endOffset)` over `Record::offset`**. Offsets never shift under append (records keep their offsets), so the last run's `endOffset` is `INT64_MAX` and appended records fall into it automatically — the "watching the last run" case needs no special code. (Filter context briefly made that contiguity load-bearing; it no longer is — see §7.2.1, where the leading window became a backward walk over in-bound rows.)
- **Detection reuses the text matcher** (the one behind message filtering and Find) against each record's **whole first decoded line** — the same shape as `recordStartRe`, and going through the `Decoder` so it is encoding-correct (invariant #8). Runs are stored on the `Document` as start markers; a run's `endOffset` and record count are derived from the next marker, so a new marker appended live *retroactively* bounds the previously last run with no mutation of existing entries. Records before the first marker form a leading "preamble" run so nothing is unreachable.
- **`Document::acceptsInView()`** combines the run bound (checked first, cheapest) with `FilterSet::accepts()`. Both `applyFilters()` and the live-append path call it, so the run restriction is applied identically on the initial pass and on tail — the run range is *not* a `FilterSet` axis (its match target differs, and keeping it on the `Document` avoids the two panes clobbering one shared struct). The visible subset it produces is the ordinary `FilteredIndex` (§7.1), so scrolling/geometry/highlight/Find are unchanged.
- **Live:** the appended tail is scanned for new markers *before* candidate admission, so a new run's records are rejected by the (now-bounded) selected run rather than admitted and later removed — the view freezes at the boundary and the new run appears in the pane to switch to (`SPEC.md` §3). Rotation/truncation re-detects over the fresh index and defaults to the last run.
- **"Last run" is a MODE, not a third value of `selectedRun()`.** The pane's first entry and its default is a standing instruction to show whichever run is last (`SPEC.md` §3a), and it has to stay one: the selection itself must name a concrete run for the byte bound, the `RunSeconds` baseline and every label, so what is sticky is the *rule* that re-points it — `Document::m_followLastRun`, set by `selectLastRun()` and cleared by `selectRun()`. Three consequences.
  - **Picking the run that happens to be last is deliberately not the same gesture as following it**, so nothing may infer the mode from `selectedRun() == runs().size() - 1`: those agree exactly while following is doing its job, and telling them apart is the whole feature. `RunPane` therefore reads `followingLastRun()`, and the entry travels to `MainWindow` as `RunPane::kLastRun` rather than as the ordinal it currently resolves to.
  - **The retarget is the CALLER's, not `updateRunsAfterAppend()`'s.** The append is mid-flight there, and the frozen boundary above is exactly what keeps two runs' records from mixing in one view; moving the selection is not an append at all but the same wholesale re-apply an explicit run switch does. So `retargetLastRun()` is a separate question, asked once per tick by `MainWindow::followLastRunIfMoved()` — which sits **above** the ingest handler's `ctx != activeContext()` early return, because a log that restarts while its tab is in the background would otherwise sit on the finished run until something else re-applied it. It rebuilds the digest, which an explicit switch does not need to: the digest is run-bounded, and here the run changed under a strip nobody asked to change.
  - **A document with no runs follows nothing and shows the whole file**, which is what a file with no run-start pattern has always shown — so the mode is inert until the first marker turns up, and is never a way to see nothing.
- **Persistence:** the run-start pattern lives in `FormatSettings` (per-file, like the format); the session records *which* run by its start offset/timestamp (a stable key, re-resolved to an ordinal after re-indexing), never the ordinal. **"Last run" saves no offset at all**, because it names no run — saving the run it currently resolves to would restore the session pinned to a run the application has since finished, the one thing it exists not to do. It rides the existing schema rather than extending it: `runAll` false with no offset already meant "nothing meaningful, fall back to the last run", which is precisely this, so no version moves and an older binary reads the file unchanged.
- **The pane presents the runs as a `QListWidget`, not a combo, and it is the one thing in the pane that grows.** A combo shows one run at a time, so what the pattern actually found — three runs or thirty, and where each starts — cost a click to learn, in the pane whose entire job is to answer that. The list is added to the root layout with **stretch 1** and there is deliberately **no trailing `addStretch`**: that stretch is exactly what pins a list to its floor with an empty gap under it, the trap `AxisEditor` records at length for the value axes (§7.2). Three consequences. Selection travels on **`currentRowChanged` guarded by `m_populating`**, not on a click signal — a list is walked with the arrow keys as much as it is clicked — where the combo could use `activated` and get "user choice only" for free; the guard is what keeps `clear()`'s `currentRowChanged(-1)` and the row being set back during a rebuild from reading as a choice, and `refresh()` runs on **every live append**. The horizontal scrollbar is switched **off** so long labels elide (with the full label on the tooltip) rather than the view widening the dock past the pane — the width trap §7.2 records for the message axis. And the rebuild preserves the vertical scroll offset, because a list the user is reading is rebuilt under them each time a run's record count ticks over. `tst_runpane` pins all four.

### 7.4 The record context menu

Right-clicking a record turns that record's own field values into filter and highlight criteria (`SPEC.md` §5). It is an **input method for `MatchCriteria`, not a second filtering system** — nothing in it can express a criterion the panes cannot. That is what makes it additive: presets, session restore, the absent-field exemptions and portability across a re-index all apply to it without a line of new code, because what it produces is what the panes produce.

Three seams, each placed where it already had everything it needs:

- **`LogView` answers only "where".** It emits `recordMenuRequested(viewRow, column, globalPos)` and builds nothing: it has the hit test and no access to the panes. The position arrives in **viewport** coordinates — `QAbstractScrollArea` forwards a context-menu event from the viewport exactly as it forwards a mouse press — and the record is resolved against the total display-line count rather than through `recordAtViewportY()`, which clamps a click below the last record to that record. Clamping is right for a click, which selects the nearest row, and wrong for a menu, which would then act on a record the cursor is demonstrably not on.
- **`MainWindow` assembles it**, because it is the only place that reaches both the record's fields (through the `Document`'s intern tables) and the panes the items edit. `buildRecordMenu()` is split from the popup and public so tests inspect and trigger items without `exec()` blocking on a real menu. Items are **omitted, not disabled**, when the record or the format cannot answer for that axis; the clicked column reorders the groups and never changes their contents.
- **The edits land on the panes' own controls** (`FilterPane::showOnlyValue()` and friends → `AxisEditor`), never on `Document::filters()` directly. The pane's widget state is not derivable from the resolved `FilterSet` — which is why the window stashes it per file (§12.1) — so a direct write would leave the pane showing something else and the next hand edit would silently undo the menu's. It is also the undo story: there is no undo stack, and the ticks visibly moving *is* the feedback.

The one thing that is genuinely new rather than borrowed is the restriction bit `showOnlyValue()` sets; see §7.2, "unless the selection is a restriction". Two smaller decisions worth keeping: a highlight item **appends** its rule, since rules are first-match-wins (`SPEC.md` §7) and a rule the user placed deliberately must outrank one added by a menu click; and setting one time bound has to answer for the other, because the editors always hold *some* wall clock and an unseeded end bound sits in the year 2000 — so the far end is pushed out to the file's observed span whenever it would otherwise make the range empty.

### 7.5 A rule's effect is a set of actions (M19)

Colouring used to be a rule's only effect. It is now one of four — colour, digest, tab marker, notification — each opt-in per rule, so a rule may match and not colour, and a rule may carry no action at all (`SPEC.md` §7). Everything below the effect is untouched: the five match axes, `MatchCriteria`, `resolve()` and the ordered list are exactly what they were.

**`HighlightActions` is a `Q_DECLARE_FLAGS` set at namespace scope**, with no `Q_OBJECT` or `Q_GADGET` — `Q_DECLARE_FLAGS` is a typedef and `Q_DECLARE_OPERATORS_FOR_FLAGS` a pair of inline free functions, and nothing here wants `QMetaEnum` reflection. `<QFlags>` is QtCore, so `loftail_core` gains no dependency.

**Serialized as an array of stable TOKENS, never as the flags integer.** A token still means what it meant after a version has learned a fifth action; a bitfield does not. Three rules, and the first two are the ones that are easy to undo:

- **`fromJson` tests `contains("actions")`, never the array's emptiness.** Absent means `{Color}` — every rule written before M19. A **present but empty** array means *no actions*, which is a deliberate state one click away (unticking Highlight) and is how a rule is parked without being deleted. Reading empty as absent silently re-colours every parked rule on the next launch. Exactly the trap the settings tree's `contains("pattern")` records for an empty saved pattern (§8).
- **`toJson` omits the key entirely for a colour-only rule**, so every preset, session and exported file that predates M19 serializes byte-identically and **neither store's schema version moves**. That matters twice over: `PresetStore` gates on exact version equality with no migration, so a bump discards every preset a user has; and a `SessionStore` bump, which does migrate upward, produces a file no already-shipped binary can read.
- **Unknown tokens are ignored, not preserved** — round-tripping them would need a string list on a struct whose point is that it is small and portable — but ignoring must not collapse into the absent case: a rule whose only token is unknown has *no* actions, because the key was there and the intent was recorded, just not in a vocabulary this build has.

- **The actions live in the rule list, which is therefore a `QTableWidget`**. They were four checkable flat `SectionBox`es stacked under an `Action` caption, below the list — one rule's worth at a time, in the pane that has the least height to spare, while the list above already had a row per rule with a summary in it and nothing else. An action is a per-rule answer of one bit, which is what a column is for: six of them (tick, summary, the colour pair, digest, notify, tab) put every rule's whole effect on screen at once, comparable down the list and settable without selecting the rule first, and hand the editor back the height its five axes were competing for. The `Condition` caption goes with it — with the other half gone there is nothing left to tell it apart from — so what is below the table is an `AxisEditor` in a `QScrollArea` and nothing else. **The editor is that scroll area's own widget**, exactly as in the Filters pane, and not a widget inside a container's layout: the container had a trailing `addStretch(1)` under it, which is the very thing `AxisEditor` deleted from its own root layout and documents at length — a stretch below the axes claims every spare pixel, so the subsystem and thread lists sat at their floors while an empty gap grew under `Time range`. With `widgetResizable`, the spare height reaches the editor and the stretch on each value axis divides it, so the two lists grow in this pane as they do in the other one. The pane's **root layout is flush** for the mirror-image reason: `AxisEditor` supplies its own `kSideMargin` and a layout margin here is *added* to it, so the style's default put a rule's `Subsystem` box 17 px from the dock edge against a filter's 6 — one set of axes, indented differently depending on which dock it was in. The table and its buttons are indented by hand to the same `kSideMargin` instead, so the pane reads as one column. `tst_highlighterpane::theAxesSitWhereTheFiltersPanesDo` asserts the two panes against **each other** rather than against the number, since the claim is that they agree. Four things this costs, each a trap:
  - **`HighlightAction::Color` is DERIVED from the two swatches and has no control of its own**: a rule colours exactly when one of its roles names a palette entry (`applyColourAction`). There is no tick left to fall out of step with the pickers, and *default* on both is what unticking `Highlight` used to be. It is applied on every ingest as well as on every edit (`normaliseRules`, called from `setDocument` and `restoreState`), because a rule can arrive from a session, a preset or another machine claiming to colour while naming no colour — which the table would then draw as two empty swatches on a rule that is silently winning the `Color` action for every record it matches, first-match-wins being per action. The one thing this *loses* is an M19-era rule holding `Color` with both roles at *default*: it shadowed lower colouring rules and now does not. That state was never reachable by clicking anything and is not expressible in the new pane at all.
  - **Every cell but two holds a WIDGET, and each widget carries its row in a `"ruleRow"` property.** A cell widget does not move when the model does, so every reorder, insert and remove goes through `reloadRuleTable()`, and that rebuild starts with `setRowCount(0)` rather than `clearContents()` — dropping the rows is what takes the widgets with them, and a survivor still carrying its old row index would write the next edit into whatever rule now sits there.
  - **`m_updating` is still saved and restored, never forced false**, for exactly the reason `loadEditorFor()` documents: the rebuild drops the current cell, which emits `currentCellChanged(-1, …)`, which re-enters `loadEditorFor()`. The builder's own `setCheckState` calls are otherwise read back as user edits — the shape of the M19 bug that switched every rule off from the second one on.
  - **The three actions are checkable `QToolButton`s, and the rule's own tick is not.** An action is answered by a glyph that stays pressed: three ticks in a row say only that three things are set, where three icons say *which* three — which is what pays for the header row being gone. The enable tick stays a check, because it is not an action: it says whether the rule runs at all, and a fourth pressed-in button beside three of them would read as a fourth thing the rule does. That one column is a delegate, since Qt lays a view item out check-then-icon-then-text from the left edge and ignores the item's alignment doing it — a column holding nothing but a tick draws it hard against its left border, a column's width from the middle of the space it answers for — and since the default hit area is the indicator itself, perhaps 13 px in a column barely wider. `CheckCellDelegate` centres it and makes the whole cell toggle it.
  - **Every column but the summary is `QHeaderView::Fixed`, measured once from a prototype**, because a cell *widget* contributes nothing to `ResizeToContents` and with the header gone there is no header item left to measure instead — the columns would collapse to nothing. The row height comes from the same measurement, since a cell widget is resized to its cell and a row sized from the summary's text would squash both a picker and a button.
- **There is no header row, and the cells carry what it used to say.** A header naming five columns with glyphs is a legend, and a legend earns its row only while the things under it cannot speak for themselves: an action button wears its own glyph in every row, and the two pickers say which role they set by the bar under the text picker's letter (see the swatch entry below). What is left is one column of prose, which needs no caption to be found. `QHeaderView::setVisible(false)`, not a stylesheet: the sections still exist and still lay the columns out.
- **An action button's STATE is in its glyph, not in its frame** — `actionGlyph()` returns a two-state `QIcon` (`QIcon::Off` a thin outline in ink at alpha 115, `QIcon::On` the same shape filled at full ink and a heavier stroke), and Qt swaps them for free because the button is checkable. Leaving it to the style does not work: a checked `QToolButton` is a panel a few percent darker than an unchecked one, which at 14 px in a dock is invisible, and in this table it is worse than invisible — a selected row tints every button in it, so the only cue for "this action is in force" was also the cue for "this is the rule being edited", and the two are read at the same glance. Outline-versus-filled is the contrast that survives, in either theme, under any style, because it does not depend on the style drawing anything. Deliberately **monochrome**: colour is what the two swatches in the next cell mean, and an action that went coloured when switched on would read as a third colour choice on the same row. Putting it in the icon rather than in the toggle handler is also what makes a rule restored from a session or a preset draw correctly with no refresh — there is no state change to miss. `tst_highlighterpane::anActionThatIsOnLooksIt` asserts it as *ink* — summed alpha, on more than half again off (measured 4.8× for the strip) — rather than as "the two renderings differ", which a one-pixel change would satisfy while the buttons went on looking the same.
- **A swatch previews the rule's PAIR, not the one colour its picker sets** — the letter is the rule's text colour and the tile behind it its background, in *both* pickers, so an entry shows what a matching record would look like if it were chosen. Only which half the entry varies differs: the text picker runs the letter through the palette over the background the rule already holds, the background picker runs the tile through it under the text colour it already holds. `swatchIcon()` therefore takes a `counterpart` colour, and it is the **resolved** one (`HighlighterPane::roleColour()` — the palette entry, or `palette().text()`/`palette().base()` for *default*, the same fallback `LogView` applies when it paints the record), because what a preview must show is what the record gets and not what the rule stores. Three consequences. `updateColourPreviews(row)` is the **only** place a swatch icon is made and it repaints **both** pickers, since a choice in either invalidates the other's entire list; `makeSwatchCombo()` adds its items with no icon at all and `buildRow()` calls it once both pickers exist, which is also why the call sits in the `currentIndexChanged` handler and not in `refreshRow()` — every other caller of that is an *axis* edit. The `kDefault` entry is deliberately **not** previewed and keeps its struck-through empty tile: previewed, the theme's own text on the theme's own base is what Ink-on-Paper already looks like, and the one thing that entry has to say is that it names no colour. And because both closed swatches then show the same pair, the **text** picker's letter gains a bar under it in the letter's own colour — the standard mark for a text-colour control, and the only cue left now that the shape cannot carry the role (a filled tile for the background, a bare letterform for the text) without giving up the preview. `tst_highlighterpane::aSwatchPreviewsTheRulesPair` pins that both colours appear in an entry of either picker, and that choosing in one repaints the other.
- **Every glyph and swatch is DRAWN, never lettered** — 14 px pixmaps painted with `QPainter`: an *A* in three strokes, a filled tile, a three-line strip, a bell, a bookmark. Not characters from a font, because the offscreen QPA plugin on Windows resolves no font at all, so one there is a guaranteed blank. `SwatchCombo` is a `QComboBox` that clears `currentText` in its own style option, so the closed state is the swatch alone while `findData()`, `currentData()` and the banded popup are untouched; the name lives in the popup, the tooltip and `accessibleName`. Every swatch is drawn **inside a hairline outline**, which is not decoration — an unoutlined Paper tile on a light theme is an empty cell, and an empty cell is exactly what the *default* swatch means. All of it is painted for the current theme, so `changeEvent(PaletteChange)` rebuilds the table and restores the selected row.
- **A body-less group box does not size itself**, which is what the three tick-only actions used to be and what the digest caption still is: with no layout its `sizeHint()` is *invalid* — `QSize(-1, -1)` — so a layout falls back to `minimumSizeHint()`, which with the title style sheet in play came back at 20 px under Breeze for a title row running to y=24, and the rows silently cut their own descenders. Only on that style: Fusion answered 37 px and looked perfect, which is why a photograph of a KDE desktop found it and no render of mine did. `SectionBox` overrides both hints to expand to `titleRowHint()` — the style's own label and indicator rects, so it is right per style rather than per font guess — and both stay pure queries, since a setter inside a size hint is unbounded recursion (`LogView::sizeHint`). `tst_highlighterpane::noSectionClipsItsOwnTitle` fails on the pre-fix code under Breeze and passes under Fusion, which is the shape of every bug in this corner.
**First-match-wins becomes per action**, and the primitive is `matchActions(rec, wanted, msg)` — **one pass over a wanted-set, not one call per action**. The live path needs Digest, Tab and Notify for the same record, and three separate calls would decode that record's message three times, which is the cost invariant #4 exists to stop. The loop keeps the existing structure (integer axes, then text, memoized across rules) and adds two lines: skip a rule unless `rule.actions & stillWanted`, and on a hit assign it to each action in that intersection and clear those bits. A digest-only rule therefore cannot shadow a colouring rule below it — it was never a candidate for `Color`. `anyEnabled(actions)` is the matching gate.

`ruleMatches(i, rec, memo, msg)` is the **per-rule** question, which first-match-wins cannot answer: a digest is one row *per rule*, including rules a higher rule would have shadowed. The memo is in/out so testing several rules against one record still decodes once.

#### 7.5.1 The alternate-index seam

`LogModel` bound to a `const Document *` and read *the* document's `FilteredIndex` in exactly four places (`rowCount`, `cellText`, `matchedRule`, `rowIsContext`); `LogView` read it in three (`recordCount`, `geom`, `copySelectionRaw`). All seven now go through **one** accessor: `LogModel::setViewIndex()` plus `viewGeometry()`/`sourceRow()` for the view — joined later by `viewRowOf()`/`viewRowAtOrAfter()`, the reverse map the filter anchor asks for (§7.1.2). A second model over the same document, pointed at a second `FilteredIndex`, is then the whole of what a digest strip needs — and a *separate* digest model class would have duplicated ~130 lines of `cellText`/`rowColors`/`matchedRule`.

`LogModel::setHighlightAction()` is the second half: `Color` for the log, `Digest` for the strip, so a digest row wears the colours of the rule that put it there whether or not that rule also colours the log. Two lines, and it is what identifies a row without a column the log format does not have.

The defaults reproduce the previous behaviour exactly, which is why `tst_logmodel`, `tst_logview`, `tst_filtercontext` and `tst_tail` pass **unaltered** — that, not a comment, is the proof the seam is inert.

**`ideas.md` #12 called the digest per-view state (invariant #7), and that is wrong on the facts.** Its ordinals derive from per-*file* rules over the per-*file* index inside the per-*file* run bound, so two views of one log could only ever compute the same list. What is per-view is the *widget*. So the `FilteredIndex` and the model are per-file and the `LogView` is per-view — invariant #7 applied, not waived. A consequence for the tests: a `DocumentView` now holds **two** `LogView`s, so `findChildren<LogView *>()` stopped counting views, and every counting site names the one it means (`"logView"`).

#### 7.5.2 The digest

For every enabled rule carrying `Digest`, the **last** record it matched; the result is the deduped union of those ordinals, published in **timestamp order**, which `FilteredIndex::setVisible()` takes as readily as any other — the same lever M15's filter context pulled one level down.

- **Deduped by ordinal, then ordered by time, and the two passes are not interchangeable.** `std::unique` needs the ordinals sorted, and two rules whose newest match is the same record must contribute one row rather than two identical ones — so the ascending sort happens first and the chronological reordering second. The reordering exists because the strip is the one place in loftail that stacks records from different points in the file: log4cplus appends in the order threads reach the appender, not in the order they stamped their records, so file order is very nearly timestamp order and, on a busy log, not quite — and the strip is read as *what happened, and when*. Nothing below it assumes an ascending list: `FilteredIndex` copies the records in the order given, and the digest never touches the incremental append path (`appendVisible`/`trailingCountFrom`), which is the one place ascending order is relied on. Every digest update republishes wholesale.
- **A record with no timestamp keeps its SLOT, and is not handed to the comparator.** An unparsed line a message-text rule matched carries `Record::kNoTimestamp`, which is `qint64`'s minimum — sorting on it pins every such row above the whole digest. The tempting fix, a comparator returning `false` whichever way an unplaceable record is compared, is worse: it is not a strict weak ordering (an unplaceable row is incomparable with both a 12:00 and a 12:05 record while those two are ordered), and a comparator that is not a strict weak ordering is **undefined behaviour** in `std::stable_sort`, not merely an odd result. So the timestamped ordinals are lifted out, sorted among themselves, and written back into the slots they came from.

- **Bounded by the selected run, and deliberately not by the filters.** The run bound because §7.3 makes it "one more bound composed into the filtered view" and §7.2.1 already ruled that context composes with it: a digest row from the *previous* run presented as the newest is that error one step worse. The filters not, because the digest answers a question about the **file** while the view is filtered elsewhere — coupling it to `applyFilters()` would empty the strip exactly when its premise applies. The honest cost, stated in `SPEC.md` rather than discovered: a digest row may name a record the main view is not showing, so the strip is for reading and copying and **does not navigate**.
- **The backward scan is fenced at `kDigestLookback` (100 000 in-bound records) — a cap, not a disclosure.** `HighlighterPane::commit()` fires on **every keystroke** in the message-text field, so an unbounded backward decode-scan would hang the window once per character typed into a digest rule on a large log. Fenced, it is bounded independently of file size. This is the M16 `wc -c` shape: fence the thing whose cost the user cannot see.
- A backward walk over the **already-built** index is not an indexer pass. Invariant #9 governs the scan that *produces* records; §7.2 already permits random access in `data()` on the paint path for the same reason.
- **`m_digestLast`** (per rule, the source ordinal of its newest match) makes an append `O(new × rules)` rather than another scan: the backward walk runs once, and afterwards a new record can only push an entry forward.
- **It republishes when the ordinal list changes — and also when the PROVISIONAL RECORD changed under an ordinal it already holds.** `FilteredIndex` copies each 32-byte `Record`, so a digest row whose record grew a continuation line — the ordinary live case — would render at a stale height for the rest of the session. Skipping the republish on unchanged ordinals is what stops a quiet tick jolting the strip, so the two needs are reconciled by `publishDigest(force)`. The main path pays the same cost with `notifyRowChanged(base)`; the digest has no equivalent unless one is written. And when the provisional record *stops* matching a rule it was the newest match of, that rule's entry is re-found by a bounded backward scan rather than left dangling.
- **The digest `FilteredIndex` is ALWAYS ACTIVE, even when empty** — `setVisible({})`, never `clear()`. An inactive `FilteredIndex` is the **identity** view: it reports every source record. That is the right meaning of "no filter" and precisely the wrong meaning of "no digest", and since the strip's visibility is driven straight off its model's `rowCount()`, an inactive empty digest would put the entire log in the strip under the log.

**The strip** is `LogView::Role::Digest` — configuration, not a subclass. Header hidden (it borrows the table's columns), both scrollbars off, no follow control, `sizeHint()` = its rows. It is **captioned**, by a body-less `SectionBox` reading "Digest" — the same title-row-and-hairline the five filter axes wear, minus the checkbox, so the one caption in the document area is drawn by the class that draws every caption in a pane rather than by a hand-styled label that would drift from them. The caption is a **sibling** of the strip and not its parent, however much a titled box wants to hold the thing it titles: `digestContentLines()` caps the strip at a third of `parentWidget()`'s height, so a box whose own height comes from the strip's size hint would cap the strip against itself and feed the layout its own output. Both visibilities are therefore set explicitly in `refreshDigestVisibility()` — a "Digest" heading over nothing is worse than no heading, and setting the view's own keeps `digestView()->isHidden()` meaning "the strip is not there". Four more things worth keeping:

- **`layoutHeader()` must ask whether the header is hidden.** It reserved a viewport top margin unconditionally, which left a header-tall blank band above a one-line strip — a rendering fault, in the one widget whose whole claim is that it is as tall as its rows.
- **`sizeHint()` stays a pure query and `refreshDigestCap()` does the mutating.** `QAbstractScrollArea::setVerticalScrollBarPolicy()` calls `layoutChildren()` whether or not the policy moved, and layout asks for the size hint — so setting the policy from inside the hint is unbounded recursion. It hung `tst_multidoc`.
- **The cap** is a third of the parent's height or twelve display lines, whichever is smaller, because a single digest record can legitimately be a hundred-line stack trace. Only where the cap bites does the vertical scrollbar return, so "not scrolled" is true in every ordinary case. The cap depends on the *parent's* height, which the strip's own resize cannot observe, so `DocumentView::resizeEvent` drives it.
- **Columns AND horizontal offset are mirrored** from the table, one way. Column state alone lines the columns up only at offset zero, and "rendered exactly as it is in the log" is then false the moment the user scrolls right.

**The strip is deliberately not connected to `recordMenuRequested`.** Its view rows are a different ordinal space and `MainWindow::showRecordMenu` resolves them against the document's own `FilteredIndex`, so wiring it up would make the menu act silently on the wrong record. It is avoided by *omission*, which is the kind of thing a later "connect everything" pass restores.

#### 7.5.3 The live match, and what the tray actually does

Highlighting was entirely lazy and pull-based: nothing matched a record until it was painted. Digest, Tab and Notify all need to know as a record **arrives**, so `LiveController::runMatchActions()` runs between `resolveHighlighters()` and `emit ingested(...)` in `ingestAppended()`. It lives there because that is the only place that knows *which* rows are new — `MainWindow` receives a count, and reconstructing the rows from it is the parallel bookkeeping §7.2.1 spent a paragraph avoiding.

**The gate is its first line**: `if (!highlighters().anyEnabled(Digest|Tab|Notify)) return;`. A document whose rules only colour therefore pays one walk of the rule list per watch tick, touching no record and decoding nothing. That single sentence is what the milestone's performance claim rests on. One honest cost to record: a text *filter* plus a text *digest rule* decodes each appended record twice, since the two passes share no memo. Bounded by batch size, and `messageText` is a single-line decode.

`AlertPolicy` (core, no QObject, no timer, clock injected) is the rate limit, in two layers: **one decision per ingest batch** by construction, so "ten thousand matches in one tick is one notification" needs no special case; and a 10 s minimum interval per log, inside which matches are **coalesced into a count rather than dropped** — dropping them would make the next notification lie about what happened while it was quiet. A **backlog pump** on a 5 s timer is required because `ingested` only fires on a tick that produced records: a burst followed by silence would otherwise never release what it suppressed. The policy is where the honest test coverage is (`tst_alertpolicy`), because the *delivery* has none: the runners are headless with no tray and no notification server.

**`QSystemTrayIcon::showMessage()` is a silent no-op unless the icon is shown**, so "notify" necessarily means "loftail puts an icon in the user's tray" — a visible thing to do to someone's desktop. It is therefore scoped to the feature: created on the first enabled rule that asks, destroyed when none does. And `isSystemTrayAvailable()` is **false on a stock GNOME/Wayland session**, which is the reference desktop, so the degrade path is the *common* path there, not a corner: the pane disables the Notify control and says why, and a rule that already carries `Notify` (from a preset, or another machine) behaves as if it carried `Tab` rather than being rewritten behind the user's back.

**The tab marker is set ABOVE the `ingested` handler's `ctx != activeContext()` early return.** That return is the lambda's first statement, and a background tab is the only case the marker exists for — put it below and the feature works perfectly in manual testing with one tab open and never fires in real use.

#### 7.5.4 The default rules are a seed, not a floor

`HighlighterSet::defaults()` is three colour-only rules on the priority axis — FATAL/Vivid Red, ERROR/Deep Red, WARN/Soft Amber, each paired with `readableTextSlot()` of its background (`SPEC.md` §7). It is a *value*, not a policy: nothing consults it except the two places a new `Document` is made.

**Where the seed enters is the whole design, and it is not `Document`.** A seed has to be applied where "has anything ever been stored for this log?" can be asked, and core cannot ask it — `Document` has no idea whether it was built by an open, a restore or a test. So the two call sites are `MainWindow::openWithSettings()` (a first open, which by definition has nothing saved) and `MainWindow::prepareContext()` (a restore, which asks the session). Putting it in the `Document` constructor instead would colour every document every test builds, which is how `tst_logview`'s pixel assertions and `tst_logmodel`'s colour ones would learn about a product decision they have nothing to do with.

**The restore asks `d.highlighters.contains("rules")`, never whether the array is empty** — the same rule `HighlightRule::fromJson` applies one level down to `"actions"` and `LogSettingsStore` to `"pattern"`, and the third store to record it. A stored empty list is the user having deleted every rule, which must stay deleted; only a session that says nothing at all about this file's rules is silence. Read empty as absent and a deleted default returns on every launch, which is a bug the user has no way to get rid of. `saveSession()` writes the key unconditionally and always has, so the seeded branch is a session written before this build — or no session. That also fixes the one-time upgrade behaviour, deliberately: a tab already open at upgrade keeps its empty list and picks the defaults up the next time that log is opened, because the conservative reading of an ambiguous stored empty is to respect it.

**Nothing about it is a version bump.** The rules are ordinary `HighlightRule`s carrying `Color` alone, which `toJson` already omits the `"actions"` key for, so a seeded rule serializes exactly as a rule written before M19 does and neither `PresetStore` nor `SessionStore` moves.

**The seed is applied after the format has settled**, in `openWithSettings()` below the `FormatOutcome::Chosen` branch that may re-`prepare()` the document, and it is followed by `resolveHighlighters()` — a rule that is never resolved is inert, and on this path nothing else would resolve it until the first scan completes.

**Order is load-bearing and is the axis's fault, not the seed's.** The priority axis is a *minimum*, so the ERROR rule matches FATAL as well; only FATAL sitting above it stops first-match-wins handing a FATAL record the ERROR colour. And no gate is needed for a format with no `%p`: every record is then `Priority::Unknown`, which `AbsentField::DoesNotMatch` already refuses to colour, so the three rules are simply inert. `tst_highlight` pins both, and `tst_sessiongui::aDeletedDefaultRuleStaysDeletedAcrossARelaunch` pins the `contains()` — it fails on the `isEmpty()` spelling.

## 8. Persistence

- `QSettings` for window geometry, `QMainWindow::saveState()` output (the pane layout), the open files and the views onto them in tab order, per-view column layout and wrap mode, and per-file filters/highlighters. The highlighters entry is the one whose ABSENCE means something: a document with no `"rules"` key at all is seeded with `HighlighterSet::defaults()`, a document with an empty one is not (§7.5.4). **Not** the format, encoding, source zone, timestamp display or run-start pattern: those are settings, resolved from the tree below on every open, which is what lets a Preferences edit reach a restored tab. Removing them earned no schema bump — a removed key is exactly what a backward read handles, and bumps are earned. Follow state is **not** persisted: every file opens at its end, following (`SPEC.md` §3), so there is nothing to restore. The schema is at version 3; see §12.3 for its shape, the two migrations, and the restore ordering.
- Presets as JSON under `QStandardPaths::AppConfigLocation` — a discrete file format, since `SPEC.md` §9 proposes export/import. Compiled only under `LOFTAIL_WITH_PRESETS`; see below.
- The **settings tree** as one JSON file, `logsettings.json`, under `QStandardPaths::AppConfigLocation` (M20): the defaults, an ordered list of file patterns, and per-log entries. It supersedes M3's path-keyed `FormatCache` and M18's `DefaultFormatStore`, whose contents it migrates in once and whose `QSettings` groups it then removes; see below.
- Schema version field in both settings and preset files from day one; migrating unversioned user data later is unpleasant.

**The settings tree is one file with three levels, and the deepest one that names a log wins WHOLE** (`SPEC.md` §4). M3 answered "what did the user choose for *this* file" with a path-keyed `FormatCache`; M18 answered "what should a file nobody has configured be tried with" with a pathless `DefaultFormatStore`. There was nothing between them, so a house layout shared by a hundred files was confirmed a hundred times. M20 adds the missing middle — an ordered list of **file patterns** — and, having done so, keeps all three levels in one place rather than three.

**Whole-node values, not per-field merging.** Each node carries a complete `LogProfile`: the seven `FormatSettings` fields plus the wrap mode a new view starts in. That is deliberately the rule the two stores already had ("a cached entry is taken whole, and the default is consulted only when there is none"), generalised rather than replaced. Per-field inheritance would need an "unset" representation for every field, and there is none to be had: `Encoding::Auto` and `ZoneChoice::Kind::Default` are *values*, and an empty pattern is the meaningful answer "ask me about every log". The cost is real and is the right one to pay — a per-log node differing in one field snapshots the rest, which is what **Promote to Parent Pattern** exists to undo.

**`wrapMode` sits beside `FormatSettings`, not inside it.** `MainWindow::applySettings()` diffs `FormatSettings` to choose the cost of a change — rescan, reparse, or repaint — and a wrap change costs nothing. Inside the struct it would read as a format change and provoke a full reindex.

**A per-log node stores no parent link.** Its parent is *derived* by running the matcher, so deleting a pattern, editing one, or reordering the list re-homes every affected log with nothing stored to go stale — and no dangling reference is representable. The Preferences tree therefore rebuilds on every mutation and reselects by node identity rather than by row.

**One paragraph of the old argument survives, one level down.** Folding the pathless default into the path-keyed array would have needed a sentinel row that every `readAll()` loop had to skip — a row that is not a row, in a structure whose whole contract is that a row is a file. The same objection now applies to the **virtual "no matching pattern" parent**, which is why that lives in the tree *widget* and nowhere in the model or the file: "no parent" is the absence of a match, not a thing to store.

**Presence, not emptiness, per node.** Reading a node's settings tests `contains("pattern")`. An empty saved pattern is a real answer — it parses nothing, so every log it applies to reaches the dialog, which is how a user asks to be consulted about each log. Reading empty as "nothing saved" would silently reinstate the built-in and make that setting unreachable. The key spellings are the ones `FormatCache` and `SessionStore` already used for the same fields, so a value still moves between stores with no mapping table.

**The version policy is migrate-upward, like `SessionStore` and unlike `PresetStore`.** `PresetStore`'s exact-equality discard is tolerable because a preset is a convenience the user can rebuild from what is on screen; this file is the only copy of a user's entire format configuration, and discarding it silently reinstates the built-in pattern for every log they own. A file written by a *newer* version is a separate case: it loads as empty **and blocks saving**, so running an older build for one session cannot overwrite a newer one's configuration.

**A wildcard's dialect is written out rather than taken from Qt, and the reason is the version floor.** `QRegularExpression::wildcardToRegularExpression()` converts in path-globbing mode, where `*` stops at a separator; the option that turns that off, `NonPathWildcardConversion`, is **Qt 6.6**, above this project's 6.4 minimum. Since a green local build on Qt 6.10 proves nothing about the reference toolchain, the ten-line converter is ours: `*` is any run of characters including `/`, `?` is exactly one, the result is anchored. A **regular expression** pattern is matched *unanchored* instead — each is the conventional reading for its kind, and the dialog says so. An invalid expression matches **nothing**, never everything.

**The migration runs before `restoreSession()`, and that ordering is load-bearing.** Both are in the `MainWindow` constructor. Restore no longer carries each document's format; it resolves through the tree like an ordinary open, which is what makes a Preferences edit reach a restored tab. Migrate after it and every restored tab opens on the built-in defaults, once, on the first launch after upgrade.

**Every open is now checked against the file, at every level.** `promptIfNoMatch` used to be `!cached && pattern.isEmpty()` — a file with a remembered format was never re-examined. It is now `pattern.isEmpty()`, so a log whose writer was reconfigured says so instead of showing a wall of plain text. An explicitly supplied pattern still suppresses the check, which is what keeps command-line and scripted opens free of a blocking dialog.

**A per-log node exists only while it says something its parent does not.** `LogSettingsTree::setFileProfile()` erases the node when the profile equals what the address inherits, and it is the single funnel every write goes through — the format dialog, the timestamp header menu, the Run pane, the wrap menu. That one rule is why opening a log leaves nothing behind, why "Promote to Parent Pattern" is self-cleaning, and why the store is written only when it actually changed rather than on every resume of a remote log.

**`setFileProfile()` can only see the half where the CHILD moved, so the other half is a sweep.** A node stops saying anything of its own just as surely when the pattern above it is edited, added, reordered or deleted — and nothing writes that node, so nothing re-tests it. Left behind, a hundred entries that agree with a house pattern go on shadowing it: the pattern is still editable and its logs no longer follow it, which is precisely the state the middle level exists to remove. `LogSettingsTree::pruneRedundantFiles()` applies the same equality to the whole list, and `PreferencesDialog` runs it in **`rebuildTree()`** — the funnel every mutation there already ends in, and the one place where "the parent moved" is a thing that can happen — plus once more in `accept()`, because `commitCurrent()` writes a node that has had no rebuild since. It is not a new rule but the existing one made total; the tree's *resolution* is unchanged by every removal it makes, which is what makes it safe to run unasked.

Two exceptions keep it honest. The **scratch node** `selectLog()` creates is spared by name (`pruneRedundantFiles(except)`) for as long as the dialog is open: it exists in order to be edited, and it starts out saying exactly what the log inherits, so an unexempted sweep would delete it between its creation and its first keystroke. And the **store still loads with `insertFileProfile()`**: a file written before the pattern that now covers it stays in the file until a person opens Preferences, because dropping it during a load nobody asked for is a change the user cannot see happening. The dialog is where they can.

**Promotion at the pattern level is deliberately NOT self-cleaning, and that asymmetry is the point.** A file node promoted into its pattern is then erased by the same `setFileProfile()` rule, because a file node is nothing but settings and it now says what its parent says. A **pattern** promoted into the defaults **stays**: it is also a matcher, and its position in the ordered list is what keeps a later pattern off the logs it claims, so deleting it for having redundant settings would silently re-home every log under it onto whatever matched next. Nothing under it needs re-pruning either — its file nodes inherit from the pattern, which has not changed. The virtual "no matching pattern" node stays unpromotable for the reason it always was: its only parent is the defaults, which is a level skipped rather than a level up.

**Highlight rules store two palette references — background and foreground — never RGB values** (`SPEC.md` §7). Each reference is a palette index into a 27-entry table, or a *default* sentinel meaning "leave this role at the theme's normal color." The palette maps each index to a light-theme and a dark-theme color, so switching themes remaps every existing rule automatically. Persisting raw colors would freeze rules to whichever theme was active when they were created — the exact problem the curated palette exists to prevent.

**The two theme variants are a nudge, not a flip, and that is a correction to the original design.** The palette shipped in M5 as twelve hues, each deep on a light theme and pastel on a dark one — so a theme only ever offered *one* tone, and the tone was a consequence of the theme rather than a choice. The consequence was measurable and total: on a dark theme the best of all 144 slot-on-slot pairs was **1.85:1**, and every slot used as a background sat between **1.13:1 and 2.09:1** against the theme's own text. There was no readable text-on-background combination at all; the light theme was the same failure mirrored, with 10 of 12 backgrounds failing under the default dark text. Tone is now the user's axis — three bands of eight hues (Deep, Vivid, Soft), each closed by a neutral (Ink, Gray, Paper) — and a slot keeps its band in both themes, shifting only enough to sit against the surrounding base.

Three numbers hold the table together, and all three are pinned by `tst_highlight::paletteEveryBackgroundHasReadableText`:

- Every slot names the neutral that reads on it (`PaletteSlot::textOn`, surfaced as `readableTextSlot()`), and that pairing clears **4.5:1 in both themes** — not in one and 3.9 in the other, which is why the answer is a single slot index rather than a per-theme one.
- The **Deep** band is luminance-*equalized* across hues (0.055 light / 0.085 dark) rather than equal in HSL lightness, which would put a deep amber miles above a deep purple. The **Soft** band is the mirror, fixed at high HSL lightness so the pastels look like a family.
- The **Vivid** band is deliberately *not* equalized — a screaming yellow is genuinely lighter than a screaming purple — but it is kept out of the **dead band** around luminance 0.16–0.21 where neither Ink nor Paper reaches 4.5:1, with both variants of a hue held on the same side of it. That constraint, not indifference, is why Vivid Red, Vivid Blue and Gray have near-identical theme variants: those hues live next to the dead band and there is nowhere to nudge them to.

**No schema bump comes with it**, because the stored value range only widened: an index that was valid before is valid now, so every saved session and exported preset still loads and still matches the same records. What it does not keep is its *colour* — the twelve old indices land in the Deep band and the head of the Vivid one — and that is the point of the change rather than a casualty of it. A schema version exists to reject data this code cannot read, and this code reads all of it.

`HighlighterPane::addRule()` — the one-click "Highlight This Subsystem" from the record menu — consequently sets **both** roles. Leaving the foreground at *default* was safe only while a theme had one tone; now that a background may be Deep or Soft by the user's choice, half of them are unreadable under the theme's own text, and *which* half inverts when the theme does. It also cycles only the twenty-four hues, skipping the three neutrals, which are foreground colors far more often than they are anyone's idea of a highlight.

Preset export/import (`SPEC.md` §9) is JSON. Because rules carry palette *indices* rather than colors, an exported preset is portable across themes by construction — the importing user's palette supplies the actual colors. Include the schema version (§8) in exported files so a preset shared today still imports after the format evolves.

**Presets are behind a build option, `LOFTAIL_WITH_PRESETS`, and it is the project's first gate that is not a dependency probe.** `LOFTAIL_WITH_SSH`, `_ARCHIVE` and `_KEYCHAIN` all default **ON** because each means "auto-detect this library if it is installed" and `LOFTAIL_HAVE_*` is the probe's *answer*. Here there is nothing to probe: the option **is** the answer, and it defaults **OFF**, so `HAVE` only mirrors `WITH` and exists so the sub-`CMakeLists` keep reading `if(LOFTAIL_HAVE_...)`. The definition is `PUBLIC` on `loftail_core` for the same reason the other three are — `loftail_ui` and the tests must see one feature state — even though `PresetStore` (core) and `PresetPane` (ui) are gated in separate files.

Three things follow, and each is a way to break it by accident. **The pane docks are tabbed through a cursor, not a written-out chain.** `MainWindow` builds `filter→highlight→preset→run`; spelling that out and deleting the middle link leaves the Runs pane docked on its own instead of tabbed with the rest, which looks like a layout bug and not a missing feature. **Nothing else in `MainWindow` needed a gate**, because `addPaneDock()` feeds `m_paneDocks` and every consumer — View ▸ Panes, the first-run one-third resize, the un-float sweep after `restoreState()` — iterates that vector; and the pane has no signal connections at all, being the one pane that binds to no document. **`AtomicJson` stays ungated**: `HostBookmarkStore` writes through it too, and it was only ever grouped with the preset store by milestone.

**A saved pane layout crosses the gate in both directions and neither needs handling.** `QMainWindow::restoreState()` turns a dock name it does not recognise into a placeholder rather than failing, so a layout written by a presets build restores in one without them (measured: returns `true`, the three panes come back tabbed and in order); and a layout written without the pane restores in a presets build with the pane present, appended to the tab group. Do not start editing the layout blob to "clean up" a stale `presetsDock` entry — the placeholder is what makes turning the option back on give the pane back.

**`tst_presetstore` is gated with the feature, unlike `tst_secretstore` and `tst_archivelocation` beside their own gates.** Those stay ungated because a *seam* survives in both configurations and has to behave identically in each. Presets leave no seam — `PresetStore` is simply not compiled — so there is nothing for the test to assert about a build without them. `tst_panechrome`, which turns on both the names and the *count* of the pane docks, therefore derives both from the same build-aware helper rather than writing four of anything.

**Growing the highlight axis set did not bump either schema version, deliberately.** A rule's axes now persist as a nested `match` object, and `HighlightRule::fromJson()` falls back to reading the original flat `matchLogger`/`minPriority` keys when that object is absent, so every preset and session written before the change keeps loading. That backward read is what makes the bump unnecessary — and the bump would have been destructive, because both `PresetStore` and `SessionStore` gate on *exact* version equality with no migration path: an unrecognised version yields an empty collection and a refused import, so bumping would silently discard every preset a user already had. For the same reason `MatchCriteria::toJson()` keeps `FilterPane`'s original key names verbatim (`minPriorityIndex`, `loggerChecked`, …) rather than tidying them.

**A saved host is keyed by its display name, not by its connection** (`SPEC.md` §3). `hosts.json` was originally keyed by `(user, host, port)` — the tuple that actually identifies a connection — which is defensible and was wrong for this list, because the thing the user picks from is a list of *names*. Two entries could differ only in a field the list does not show, and then neither could be told from the other nor removed on purpose: `remove()` took the connection tuple and deleted whichever row matched first. Keying on `displayName()` (the label, or the host when there is none) makes the visible identity the real one, so `save()` overwrites in place and `remove()` takes a name. The comparison is trimmed and case-insensitive for exactly the same reason — `Prod` and `prod ` are one row as far as anyone reading the list is concerned.

Two consequences worth keeping straight. `all()` drops later duplicates rather than trusting the file, because a file written before this rule — or edited by hand — can still hold them, and the whole point is that such rows must not reach the list. And `find()`, which maps an `ssh://` address to a bookmark for its auth choice and poll cadence, still matches on the connection tuple and now takes the *first* hit: an address carries no name, one connection may legitimately be saved under several, and every one of them describes the same machine.

**No schema bump for it.** The stored shape is unchanged — the same keys, the same version — and only the meaning of the key changes on the read side, so an existing `hosts.json` keeps loading. This is the same reasoning as the highlight-axis change above: the exact-version gate makes a bump destructive, and there is nothing here a backward read cannot handle.

**And `find()` finally has a caller (M14).** Until then it had none anywhere in `src/` — only tests — so the `password`, `auth` and `keyFile` it was written to deliver were persisted and never read at connect time, and a bookmark's remembered password did nothing at all. `MainWindow::primeRemoteCredentials()` calls it from the top of `openFile()`, the single funnel every entry point goes through, and hands the password to the transport the only way core will take one: through the per-target credential cache (§6.3.2). `indexOfTarget()` is its inverse for `passwordAccepted()`, which is handed a target and nothing else; it compares *forwards* — `locationFor({}).target() == target` — rather than parsing `user@host:port` apart, because `target()` emits `host:port` with no `@` when there is no user, and an IPv6 literal carries colons of its own. Still unread: `pollMs` and `tailStartBytes` reach the transport only from the Open Remote dialog and the Remote Hosts menu, so the same URL arriving from the command line, recent files or session restore ignores them — deliberately left, since priming `tailStartBytes` would change what a restored tab shows.

### 8.1 Concurrent instances

`SPEC.md` §3 allows multiple instances at once, which makes settings a shared mutable resource across processes. Three consequences:

- **Write atomically.** Preset and settings files are written to a temp file and renamed, so an instance crashing or two writing at once can never leave a truncated file. `QSettings` handles this for its own store; the JSON preset file is ours to get right.
- **Per-file state is keyed by file path**, so instances viewing different logs never contend. `logsettings.json` is the exception in shape but not in rule: it is one file holding every log's settings, written whole and atomically, so it is last-writer-wins like any other global. `showPreferences()` therefore re-reads it before showing the dialog rather than trusting the copy the window started with. This is the main reason the per-file scoping in `SPEC.md` §10 is worth having beyond its UX merit.
- **Global state is last-writer-wins** (`SPEC.md` §10), since instances have no coordination channel. Write on change rather than only at exit, to narrow the window in which one instance's state is lost.

Deliberately *not* doing: a lock file, a single-instance server, or inter-instance IPC. Each adds a failure mode (stale locks, port conflicts) far more annoying than the state loss it prevents.

### 8.2 Chrome colours, and the placeholder Qt forgets

A log's own colours have been theme-aware since M5: highlight rules reference a `HighlightPalette` slot by index, and each slot carries a light and a dark variant (§8). The **chrome** around them was not. An invalid pattern's red, a caution's amber, a muted aside and the grey of placeholder text were each a hex literal chosen against a light theme — `#c0392b`, `#b9770e`, `#b04a00`, `color: gray` — and on a dark palette they ranged from dim to unreadable. `UiColors` gives those four the same treatment, as plain functions of a `QPalette` so they need no `QApplication` and track whatever theme the widget is actually in. It is deliberately *not* part of `HighlightPalette`: those slots are a user-facing palette that rules reference by index and presets round-trip through, while these four are internal and nothing persists them.

**The placeholder is a Qt gap rather than a loftail one, and it is worth naming.** `QPalette::PlaceholderText` arrived in Qt 5.12. A platform theme that predates it — or simply does not fill it in, which is common — leaves the role at Qt's built-in default of **black at 50% alpha**, no matter how dark `Base` is. Every placeholder in the application then renders black on a dark field: present, occupying space, unreadable. It was reported from a real desktop, and the diagnosis is repeatable from a screenshot alone — the *placeholders* were black while the typed values beside them (`22`, `1000 ms`) were light, which no theme would do on purpose.

`ensureReadablePlaceholder()` repairs it, and two properties of how are load-bearing:

- **Conditional, not unconditional.** A theme that set the role sensibly is left completely alone. Overriding it everywhere would replace a deliberate choice with a computed one and make loftail look wrong on the themes that were already right.
- **Measured, not inferred.** The test is the WCAG contrast of the *composited* colour against the field, not "did the theme set this role". That also catches a theme that sets the role badly rather than not at all, and compositing matters because the failing value carries 50% alpha — comparing it uncomposited measures a colour that is never drawn.

The repair writes a widget palette, which does not follow a later live theme switch; the colours are recomputed the next time the widget is built. Worth knowing, not worth a palette-tracking mechanism for a hint colour.

**"Measured" applied to the placeholder and not to the four colours above it, which is how the amber stayed wrong for four milestones.** `relativeLuminance()` and `contrastRatio()` were correct, and private to `UiColors.cpp`, so the only thing in the codebase able to state a contrast ratio was the one function that computed one about somebody else's colour. `kWarningLight` — the caution amber, `#b9770e` — measured **3.2:1** against a light dialog: under the 4.5 bound for body text, on the sentence that says a password is about to be written to disk in the clear. `tst_uicolors` had asserted it since it was written, at **3.0**, the allowance for *large* text, which nothing here is.

Both are now fixed in the same place. The helpers (`relativeLuminance`, `contrastRatio`, `compositeOver`) are public in `UiColors.h`, the test bound is 4.5, and `kWarningLight` is `#8f5c00` — same hue, 4.9:1. The general form of the mistake is worth keeping: a threshold chosen for one call site and then applied to a second where the reasoning does not hold is invisible precisely because it is a passing assertion. The test now also checks the exported helper against its own re-implementation, so the two cannot drift while both look right.

**The log table's alternating band is the same class of defect, found the same way and fixed in the same file.** Every other record was `base.lighter(108)`, which scales the HSV *value*: on the near-black table of a dark theme that moves a couple of levels (`#141618` → `#16181a`, **1.02:1**), and on a pure white one the value is already at its maximum and it moves nothing at all — a zebra that was dead at both ends of the range and visible only on the mid-tone themes nobody runs. `alternateRowColor()` is a fixed step from `Base` toward `Text` instead, which lands near 1.13:1 on both and gets the *direction* right on each with no per-theme constant. `QPalette::AlternateBase` is the role that ought to say this and is deliberately not read: nothing obliges a theme to make it differ from `Base`, and a theme that leaves them equal takes the band away again — silently, and on exactly the mode that needs it most, since in wrap-always-on the band is the only thing marking a record boundary.

Two properties of *where* it is applied carry the rest, and both are in `LogView::resolveRowColors()`. The band is keyed on the **view row, which is a record** (invariant #2), and the caller fills the whole record's rect with the answer — so the alternation changes at a record boundary and not at a line. And it lives in the `else` of the highlight-rule branch, so a rule-coloured record is never tinted: two adjacent records matching one rule paint as a single unbroken block of its colour rather than as two shades of it. `tst_logview::theAlternatingBandChangesAtRecordsAndNotAtLines` renders the viewport and reads both claims back off the pixel runs down one column, which is the only place either is observable.

## 9. Format autodetection

Built after the manual path (M8), behind a seam that existed from the start:

```cpp
class IFormatProvider {
    virtual Expected<LogFormat, Error> formatFor(QByteArrayView sample) = 0;
};
```

`ManualFormatProvider` (reads the user's pattern from settings) came first; `DetectingFormatProvider` was added in M8 behind the same seam, and falls through three layers, cheapest first:

1. **Candidate scoring.** A library of known patterns — log4cplus defaults plus common house styles. Compile each, run over the first ~200 records, score by match rate. Resolves the common case in milliseconds with no inference.
2. **Structural inference.** Tokenize a sample; find positionally stable fields. The strongest anchor is priority: `TRACE|DEBUG|INFO|WARN|ERROR|FATAL` is a closed six-word vocabulary, so a token column drawn from it is near-certainly `%p`. A leading date-shaped run is `%d`; a dotted identifier adjacent to the priority is `%c`; a bracketed run between the logger and the message is `%x`; the remainder is `%m`. Synthesize a pattern string and hand it to the same `PatternCompiler`.
3. **Give up** and fall back to the manual dialog.

Two constraints on layer 2, both learned the hard way:

- **A synthesized pattern may never carry a multi-digit literal.** If the date shape is not recognized, the sample's own digits get copied through as literal text, producing a pattern that matches only the records sharing that timestamp. Match rate cannot detect this: scoring runs over the head of the file, where a startup burst routinely puts every sampled record in the same second, so the memorized pattern scores 1.0 and then indexes a handful of records out of a million. Refuse to synthesize it and let layer 3 ask the user.
- **Slash dates need an order decision.** `03/12/26` is 12 March or 3 December and nothing in the text says which. The order is inferred once over the sample — a component above 12 can only be a day — and defaults to month-first, which is what log4cplus's `%D{%m/%d/%y}` produces. Getting this wrong is silent: both orders compile to the same regex and score identically, and only the parsed `Record::timestamp` differs (§5.1).

Detection produces a *pattern string*, never a bespoke parser — it reuses the entire P1 path. It also requires no new UI: it pre-fills the existing format editor for confirmation, which is the second reason to build the manual path first.

**The controls that edit a format are a widget, not a dialog (`FormatEditor`, M18).** Two dialogs edit exactly the same set — `LogFormatDialog` for one file, `PreferencesDialog` for the default a never-seen file is tried with — and the pattern field, the Detect button, the encoding, the source zone and the live preview are the whole of both. Two copies would drift, and the one that drifted would be whichever the user reached for second. So the dialogs are shells: a title, the editor, their own one extra control (a "use for new files" checkbox; a "forget remembered formats" button), and a button box.

Two things the editor must keep doing. It **carries through the fields it does not own** — `timeDisplay` and the `runStart*` triple — because `settings()` builds a fresh `FormatSettings`, so dropping them would silently reset the timestamp mode and clear the run-start pattern on every pattern edit. And it accepts an **empty sample** as an ordinary state rather than an error: Preferences is reachable with no log open, which is exactly when someone sets a default up, so the preview is simply blank and Detect is disabled.

## 9.1 Localization: translatable, untranslated, and why Qt has to be told

loftail ships **no** catalogue and is English-only. Every user-facing string nonetheless goes through `tr()`, and one small piece of machinery exists to hold the two facts together.

**The bug that forced it.** On a non-English desktop, a loftail dialog rendered ten English labels above two buttons reading `Відкрити… / Скасувати`. Nothing in loftail did that: a `QDialogButtonBox`'s standard buttons, a `QMessageBox`'s Yes/No and the standard shortcut names all come from Qt's `qtbase_<lang>` catalogue, loaded for the system locale by a layer above the application — Qt itself in some builds, the platform theme plugin in others (KDE's does). A translator installed by a plugin cannot be reached to remove, and the loading is not portably suppressible.

**So the language is stated, not inferred** (`UiLanguage.h`, called from `main()` before the command-line parser and before `MainWindow` — both build their user-visible text once, in a constructor, and never re-read it). `installUiLanguage()` looks for a `loftail_<lang>.qm` matching the user's preferences; finding one, it installs that *and* Qt's `qtbase_<lang>` for the same language. Finding none — which is always, today — it installs a `SourceTextTranslator` that answers every lookup with the source text.

The ordering is the whole mechanism. `QCoreApplication::installTranslator()` **prepends**, and `translate()` stops at the first non-null answer, so the last translator installed is consulted first. The pin does not remove Qt's catalogue; it answers ahead of it. Two details that make it safe: an empty source falls through (returning null) so nothing else is starved, and `QLocale` is untouched, so dates, numbers and `formattedDataSize()` stay in the user's own format — what language a button speaks and how a date is written are different questions, and only the first one loftail is answering here.

**What is and is not translatable** is the part a later sweep will get wrong, so it is stated as a rule in `CLAUDE.md` and enforced by reading the `lupdate` output: prose is; object names, JSON and `QSettings` keys, regex fragments, log4cplus conversion patterns, Qt date codes, `priorityName()`, shell command text and the `ssh` scheme are not. Nothing in `src/core` is a `QObject`, so core files carry a one-line `Q_DECLARE_TR_FUNCTIONS` shim named for the type — the form `lupdate` understands for free functions, which the alternative (a hand-rolled file-local `tr()`) is not.

**One real bug fell out of the conversion**, and it is the reason to do this before a translation exists rather than after. `SshPromptDialogs` told its two reject-role buttons apart with `button->text().contains("Remaining")`. Both are `RejectRole`; the label was the only discriminator. The first translated build would have turned *Skip All Remaining* into an ordinary Cancel — silently, in the bulk-restore path, which is exactly where nobody is watching. It compares button pointers now.

`Qt6::LinguistTools` is an optional `find_package` component gated like every other extra (the reference build is a stock Ubuntu toolchain), exposing a `loftail_lupdate` target that nothing depends on. The generated `translations/` directory is git-ignored: there is no catalogue to keep in sync, and committing 369 empty English entries would only create one.

## 10. Testing

- **`PatternCompiler`** — the bulk of unit testing. Table-driven: pattern in, expected regex behavior and field map out. Cover every modifier, malformed patterns, and patterns missing `%p` or `%c`.
- **Indexing** — small fixture logs covering multi-line records, unparsed leading lines, CRLF vs LF, empty files, and a file ending mid-record.
- **Encoding** — the same fixture log stored as UTF-8, UTF-8 with BOM, UTF-16LE, and UTF-16BE must produce byte-for-byte identical indexes apart from offsets. This is the cheapest possible guard against the §6.1 line-terminator trap.
- **Geometry** — prefix-sum lookups against a synthetic index with known line counts, in both exact and estimated modes; assert that estimated mode converges to the exact total once every block has been visited.
- **Tailing** — a test harness that appends to, truncates, rotates and REWRITES IN PLACE a temp file, asserting the model converges to the right state. The rewrite cases are the ones no metadata check can catch (§6), and the append case beside them is what keeps the content check from turning every growing log into a rescan.
- **Model/filter** — assert filter predicates against a synthetic index without any UI.
- Everything except the view layer must be testable without a `QApplication`; keep parsing and indexing free of UI dependencies.

## 11. Performance targets

Provisional, to be validated against a real log early rather than assumed:

- Index ≥ 100 MB/s single-threaded on a warm file.
- Scrolling stays at 60 fps on a 1 GB file.
- Toggling a filter on 1M records repaints in < 100 ms.
- Live tail appends visible within ~200 ms of a write.
- Rebuilding block prefix sums after a filter change: < 20 ms per million records.

**Filter context (§7.2.1) is bounded by the same numbers with one caveat worth stating: it widens the *visible* set, and the compact index holds a 32-byte `Record` copy per visible row.** A sparse filter at `-C 50` can approach a hundred records shown per match, and in the limit a second copy of the whole record index. The pass itself does not get more expensive — still one full predicate per record, plus the backward walk per match, which stops at `lastEmitted` and so costs O(n) integer checks across a whole scan however sparse the stream is, and never a decode for a context row. The memory is the reason `Document::kMaxContext` exists and the spinners are capped rather than open-ended.

## 12. Multiple documents: contexts, views, and the window shell

Several logs are open at once as tabs in a central document well, and one log may be open in several views (`SPEC.md` §5a). This section was previously a list of accommodations for a deferred feature; it now describes the implementation those accommodations bought — the four constraints below (§12.1–12.4) held, and the work was additive.

### 12.1 Three scopes, and what belongs in each

The load-bearing distinction is that a *file* and a *view onto it* are different things.

| Scope | Type | Holds |
| ----- | ---- | ----- |
| Per file, below the UI | `Document` (`src/core`) | source, format, decoder, `RecordIndex`, `FilterSet`/`FilteredIndex`, `HighlighterSet`, zones and the timestamp display mode, runs and the run selection |
| Per file, in the UI | `DocumentContext` (`src/ui`) | the `Document`, its `LogModel`, `IndexController`, `LiveController`, `FormatSettings`, indexing progress, the Filters pane's per-file widget state, and the list of views |
| Per view | `DocumentView` (`src/ui`) | a `LogView` and its own `FindBar`; and inside the `LogView`, scroll position, selection, wrap mode, `QHeaderView` column layout, and follow state |

**Filters, highlighters and the run selection are document-scoped, not view-scoped.** Making them per view would need a `FilteredIndex` per view, which cascades into a per-view row space in `LogModel`, a per-view branch in `LiveController`'s in-place append admission (§7.3), and a Runs pane that could no longer bind by `activeDocumentChanged(Document*)`. Two views of one file therefore show the *same records* and differ only in how they are being read — which is also what a single global set of panes can coherently express.

**Wrap mode is per view, and the settings tree only SEEDS it** (M20). A node carries the mode a *newly created* view of that log starts in; `createView()` reads it, the view owns it from then on, and `SessionView::wrapMode` still restores each view's own. Invariant #7 is intact: what the node holds is a default for a view that does not exist yet, not a property of the file. View ▸ Line Wrap does write back to the log's node so the choice sticks, which is also why `MainWindow::m_wrapMode` — the old window-wide seed — is gone: two seeds for one question is one too many, and the root node is now the global answer.

**Follow state is per view** and lives only in `LogView`. `Document` deliberately has no `following` flag: pinning one view to a point in the history while another tails is the main reason to split a file at all.

**One `LogModel` backs all of a file's views.** The model carries no view state (only the light/dark cue), and each `LogView` constructs its own `QHeaderView` and `QItemSelectionModel` — the ordinary Qt multi-view case. A second model would double the append and reset traffic and buy nothing.

**The timestamp display mode is per file, despite being chosen from a per-view widget.** Its control is the timestamp column header's context menu (`SPEC.md` §4) and the header is per view, but the mode itself sits in `FormatSettings` beside the source zone it replaced. Per view would mean the shared `LogModel` could no longer format the Date column — it carries no view state — pushing that formatting into `LogView` for one setting's sake. The menu is built once, owned by the window, and its checkmark is refreshed from the active context by `updateActionStates()`, the same shape as the per-view `m_followAction`.

### 12.2 The window shell: a document well, and docks around it

The window is a **central `QTabWidget` holding the open files**, with the four side panes as the only `QDockWidget`s. The separation is the point (`SPEC.md` §5a): Qt's dock areas cannot encroach on a main window's central widget, so a pane can never be dropped into the document area and a log can never be dragged out into the panes' — no bespoke drag policing, just the one structural fact.

- `setDockOptions(AnimatedDocks | AllowNestedDocks | AllowTabbedDocks)` must be set **before any dock widget is added**. It governs the panes alone.
- **No `GroupedDragging`.** It makes a drag on any dock's title bar move that dock's entire tab group — and the panes ship tabbed together, so pulling Filters out took the other three with it. Dropping it also lifts the old ban on `setAllowedAreas()` (which `GroupedDragging` mishandled), so panes are now restricted to the left and right areas, matching `SPEC.md` §8 and removing the accidental full-width strip above or below the log.
- **Panes do not float under Wayland** (`panesMayFloat()`, keyed on the QPA platform name, not the OS). Tearing a dock off needs two things Wayland withholds from clients: pointer motion after the pointer has left the widget, and the ability to place a top-level window under the cursor. Qt says the first part out loud mid-drag — *"This plugin supports grabbing the mouse only for popup windows"*. What Wayland does provide is an **implicit** grab for the duration of a button press, delivered to the surface that received the press; a drag that stays inside the main window therefore works, while a tear-off moves the dock to a new surface mid-gesture and loses the rest of it, stranding the pane. `restoreSession()` also un-floats any pane a saved layout brings back floating, so a session written elsewhere (or before a wedged drag) cannot resurrect an unplaceable window.
- **The pane title bars are repainted, not removed** (`PaneTitleStyle`). Because the panes ship tabbed, Qt's dock title bar prints each pane's name a second time directly under the tab that already carries it, above two hairline buttons that are hard to see on a dark palette and hard to hit. The obvious fix — hide the bar — is **not available**, and all three routes were measured rather than assumed: a dock can be dragged only by Qt's *own* title bar; a custom title bar widget never receives the drag and Qt exposes no public way to start one; and dragging a tab in the dock tab bar only reorders it. Hiding the bar would therefore make §8's "dragging a pane moves that pane" unreachable in the default layout. So a `QProxyStyle` installed **on the pane docks only** blanks the title *text* while the dock is tabbed and draws larger, higher-contrast button glyphs. Two details are load-bearing: the text is suppressed at paint time rather than by clearing `windowTitle()`, which is also where the tab bar gets its label; and "am I tabbed" is asked on every paint rather than cached, because Qt has no tabification-changed signal and, when a tab group changes, **only the dock that moved emits anything at all**. `tst_panechrome` pins both the loftail behaviour and the three Qt constraints — if a future Qt lets a tab drag undock, that test fails and the cheaper design becomes available.
- The central widget is a `QStackedWidget` over the tabs and the "no file open" notice, so an empty window shows the notice rather than an empty tab frame.
- A file name is `&`-escaped before it becomes tab text: `QTabBar` reads `&` as a mnemonic.
- Two views of one file are numbered by **tab position**, not creation order, so a dragged tab never ends up labelled `[2]` to the left of `[1]`. `QTabBar::tabMoved` renumbers.

**This was originally the opposite decision**, and the reversal is the interesting part. Open files were `QDockWidget`s too, which bought drag-to-split, tab groups and floating logs for free from Qt's dock dragging. It was rejected in use: with one arrangement shared by panes and logs, ordinary pane dragging could tab a Filters pane on top of the log being read, or wedge a log into the strip along the edge. The flexibility was real, and worth less than knowing where the log is. What the earlier notes recorded as an accepted trade-off versus a third-party docking framework (KDDockWidgets, Qt-ADS) — "nothing structurally prevents a pane from being tabbed next to a log, as Visual Studio's separate document well would" — turned out to be the whole problem, and a plain central `QTabWidget` buys the document well without vendoring either library into a three-platform packaging story.

The cost is deliberate: **logs no longer split, tear off, or float.** Two views of one file still scroll independently, but side by side is not available; if it is wanted back, it belongs in a splitter *inside* the document area, never by returning the logs to the dock layout.

**Which view is active is which tab is current.** `QTabWidget::currentChanged` is the single signal for it — the earlier `QApplication::focusChanged` walk existed because a raised dock did not necessarily take focus, and a non-current tab page cannot be focused at all. `activeDocumentChanged` is emitted only when the underlying **`Document`** changes, so moving between two views of one file does not rebind the panes — which would otherwise reset the Filters pane's discovered-value state for no reason.

**The Filters pane needs an explicit hand-off.** `HighlighterPane` hydrates from the `Document` it binds to (and syncs rules back on every edit), so it needs nothing. `FilterPane`'s widget state is *not* derivable from a `FilterSet`, so the window stashes it into the outgoing `DocumentContext` and restores it into the pane on the way in; an empty stash means "the defaults", which is what a newly opened file gets.

### 12.3 Session schema v3, and the restore ordering

```json
{ "schemaVersion": 3,
  "geometry": "...", "windowState": "...",
  "documents": [ { "path": "...", "format": "...", "timeDisplay": "utc", "filters": {}, "highlighters": {}, "runAll": false } ],
  "views":     [ { "document": 0, "columnState": "...", "wrapMode": 0 } ],
  "activeView": 0 }
```

Two arrays, matching the two scopes: N files, and N views pointing back at them. **The `views` array is in tab order**, which is all the layout an open file has now; `windowState` is `QMainWindow::saveState()` and carries the pane arrangement alone.

**Restore order:**

1. `restoreGeometry()`, then `restoreState()`. Every dock — i.e. every pane — already exists, so nothing is left to place afterwards.
2. For each saved view, in order: build its file's `DocumentContext` if this is its first view (`Document::prepare()` — the fast, synchronous half of an open), then create the view, which appends its tab. Appending in saved order *is* restoring the layout.
3. Activate the saved view, then start every indexing worker. Indexing goes last so worker batches never race the layout settling.

`activeView` is an **index into the saved array**, resolved during step 2 rather than afterwards: a skipped file shifts every index after it, so the view it names has to be recognised as it is created. A file that has gone missing is skipped with an inline notice and no dialog (`SPEC.md` §10); its tab simply never appears, and if it held the active view the first surviving tab takes over.

**v1 and v2 are migrated, not discarded** — v1 as one document with one synthesized view carrying the column state that used to live on the document; v2 as-is, minus the per-view `dockName` that tab order replaced. Both `windowState` blobs are deliberately **dropped**: v1's describes a window laid out nothing like this one, and v2's records the *collapsed* central widget of the all-docks shell, which would restore the document well at zero width — a silent failure that reads as the tabs having vanished.

**`timeDisplay` was added *within* v2, not as a version of its own.** It is one additive key in the existing shape, read with the legacy `displayZone` key as a fallback (the `"local"`/`"utc"` spellings are shared deliberately), so such a store round-trips through either build. A bump is earned by structural change — a new array, a field moved between scopes, a renamed key, a dropped blob — as v1→v2 was and v2→v3 was; and it costs every session whose version `load()` does not list.

### 12.4 The constraints that made this additive

For the record, since they still bind:

1. **A `Document` owns all per-file state.** Nothing outside it may hold per-file state; `DocumentContext` holds the *machinery* around one file, not the file's state.
2. **No singletons or globals for file state.** No `currentFile()` accessor, no static index. This is the constraint most easily violated by accident and the most painful to unwind.
3. **Panes bind to the active document by signal, not by construction.** A pane built against a fixed `Document&` works fine with one file and has to be torn apart for two.
4. **The settings schema stores arrays.** It held a one-element `documents` array from day one, which is why v2 could add `views` beside it instead of restructuring — and why v3 could drop the window-layout coupling from `views` without touching either scope.

## 13. Sanitizers

`-DLOFTAIL_SANITIZE=address` builds with ASan + UBSan + LeakSanitizer; `=thread` builds with ThreadSanitizer. Off by default, mutually exclusive, and applied at the top level with `add_compile_options`/`add_link_options` rather than per target — a sanitizer is only sound when every translation unit linked into a binary agrees, and that includes all 56 test binaries.

**ASan is a CI gate; TSan is not.** That asymmetry is measured, not a preference, and the reasons are below.

Leak detection runs with `detect_stack_use_after_return` on, and **nothing of loftail's is suppressed**. `tests/lsan.supp` holds one third-party entry: libproxy, which Qt `dlopen`s from `QTcpSocket::connectToHost` to answer a system-proxy query and which never frees its GObject manager — six allocations, 141 bytes, with no loftail frame below `px_proxy_factory_new`. It appears on the ubuntu-24.04 runner and not on a 26.04 box with a newer libproxy, and only when `SshFetcher`'s background reconnect gets as far as opening a socket; that intermittency is why it is named rather than left to resurface as a flaky red build. The rule for that file is in its header, and the by-design fetcher retention deliberately does not use it (§13.3).

### 13.1 Why core uses `std::mutex`, not `QMutex`

`src/core` contains no `QMutex`, `QMutexLocker` or `QWaitCondition`, and must not regain any. This is a testability constraint, not a style one.

Qt ships TSan annotations in `qtsan_impl.h`, and `qmutex.h` calls them inline around `QMutex::lock`/`unlock`. Those annotations are compiled into *loftail's* translation units, because `__SANITIZE_THREAD__` is defined there — but the system `libQt6Core` is not built under TSan, so nothing inside it annotates anything. `QWaitCondition::wait()` unlocks and relocks the mutex **inside that library**, unannotated, so TSan's happens-before chain breaks at every wait. Data that is correctly guarded then reads as a race, with both accesses reporting the same held mutex.

Measured on one stress harness against **known-good** code: 37 reports with `QMutex` + `QWaitCondition`, **0** with `std::mutex` + `std::condition_variable`. The 37 were loudest about `GuiCallGate` — the file that had just been fixed — and pointed at nothing. TSan understands `std::mutex` and `std::condition_variable` because they go through pthreads, which it intercepts.

The ban stops at `src/core`. `src/ui` is Qt's own thread and Qt's own primitives are fine there; test scaffolding may use `QMutex` too, since a plain `QMutex` with no condition variable annotates symmetrically and is visible to TSan.

**One consequence in tests:** `QThread::wait()` joins through a `QWaitCondition`, so TSan sees no join and reports a worker's last writes against whatever reuses its stack. Where a test's own load generator is involved, use `std::thread` and `join()` — `tst_gatestress` and `tst_archivemembers` do, and say why inline.

### 13.2 Why ThreadSanitizer is not a CI gate

Two things stop it, one fixable and one not.

**The fixable part is noise, and it is fixed.** After §13.1, the tests that exercise loftail's own threads report **zero** races with `tests/tsan.supp`. That file suppresses only Qt's own queued-connection marshalling and `QThread` bookkeeping, by function name; nothing is suppressed by file or by library, because `called_from_lib:libQt6Core.so.6` would match nearly every stack in the process, loftail's own races included. The rule for adding an entry is in the file: both sides of the report must be inside Qt. UI tests are *not* covered — driving widgets and a real event loop produces 11–23 reports each from Qt and glib internals — which is what the `threading` CTest label exists to exclude. Run it with:

```bash
cmake -S . -B build-tsan -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DLOFTAIL_SANITIZE=thread
cmake --build build-tsan
QT_QPA_PLATFORM=offscreen \
TSAN_OPTIONS="report_thread_leaks=0 suppressions=$PWD/tests/tsan.supp" \
  ctest --test-dir build-tsan -L threading --output-on-failure
```

`report_thread_leaks=0` is required and is a design consequence, not a workaround: nothing joins a fetcher (§6.3.3), so a retired one whose thread is still running is a thread leak by construction.

**The unfixable part is the sanitizer runtime itself.** TSan's thread registry aborts with `CHECK failed: ... live_.try_emplace(user_id, tid).second != 0` inside `pthread_create`, called from `QThread::start` — a `pthread_t` recycled from a Qt thread the runtime never saw retired. It kills **6 of the 17** labelled tests before they finish, identically under **GCC 15 and clang 21**, and it predates this work. The other 11 complete clean.

So TSan earns its keep as a tool a developer points at a specific test, and it would not earn its keep as a gate: a third of the runs would be red for reasons that say nothing about loftail. If a future Qt or sanitizer runtime fixes the registry crash, the label and the suppression file are already in place and the job is a copy of the ASan one.

### 13.3 What the sanitizers actually found

Recorded because it calibrates what each is worth here.

- **A dangling reference in `tst_session`** (ASan, first run): `SessionStore::load(s).documents.first()` bound to a `const &`. Lifetime extension does not reach through a member call returning a reference, so six `QCOMPARE`s read freed memory. It had always passed.
- **An invalid downcast in `MainWindow::onViewDestroyed`** (UBSan): `static_cast<DocumentView *>(obj)` on a `QObject *` whose `DocumentView` subobject is already destroyed — `~QObject` runs last, so by then the dynamic type has degraded to `QWidget`. The comment already said "compare it, never dereference it"; the cast itself was the undefined part, and it went unnoticed because the bases are all primary so the pointer value came out right. Now compares in the safe direction.
- **A data race on `FakeRemote`'s call counters** (TSan): plain `int`s bumped on the thread driving the fetcher and read by a test watching from another. Test-only, real, now atomic.

**And what neither found: the M17 call-gate bug they were prompted by.** Sixty twelve-way-parallel ASan runs of `tst_remoteopen` against the pre-fix tree reproduced nothing — the slowdown closes the 1-in-28 window — and TSan never flagged the unlocked `abandoned` read, because no test went near the state that mattered. **Sanitizers amplify coverage; they do not create it.** That is what `tst_gatestress` is for, and why it is checked in beside them: it fails five times out of five against the pre-fix gate on its own, with no sanitizer at all.
